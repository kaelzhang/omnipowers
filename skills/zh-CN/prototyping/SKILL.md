# 原型制作

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 定义

原型 — 用来回答一个已写明的设计问题的一次性代码。

## 先写问题

编写任何原型代码前 → 你 MUST 在原型入口文件顶部或旁边的文件中，用一两句话写明设计问题。

## 选择分支

- 问题涉及**状态、逻辑、状态转换、数据结构或 API 使用体验** → 读 @logic-prototype.md 并照做。
- 问题涉及 **UI、布局或信息层级** → 读 @ui-prototype.md 并照做。
- 问题在上述两类之间无法确定归属时 → 你 MUST 在构建前询问用户具体要回答哪类问题。

## 原型管理规则

任一分支的每个原型，你 MUST：

1. **明确标注为一次性代码。** 在路径或文件名中放入 `prototype`；遵循宿主项目现有约定，将原型放在所探索代码附近，不创建新的顶层结构。
2. **一条命令运行。** 宿主项目有任务运行器时 → 你 MUST 将原型接入任务运行器（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`、…），通过一条命令启动；宿主没有任务运行器时 → 单条运行命令 MUST 写在设计问题旁边。
3. **状态只留在内存。** 将状态保存在内存中，重启时重置；处理原型存储时 → 你 MUST NOT 将原型接入真实数据库或持久化存储；写明的问题本身涉及持久化时 → 你 MAY 接入持久化，但仅限名称标明可丢弃的临时存储。
4. **跳过所有打磨。** 省去测试、抽象，以及维持原型运行以外的错误处理。
5. **直观呈现内部状态。** 每次操作或切换变体后 → 原型 MUST 打印或渲染完整的相关状态。

## 用户主导

- 交接时 → 你 MUST 提供能运行的产物、运行命令或 URL，以及操作说明。
- 声明问题是否已得到回答时 → 你 MUST NOT 凭自己的运行结果宣称问题已得到回答。

结论 — 用户的观察，只由用户给出。

## 记录协议

用户给出结论时 → 你 MUST 将结论记录在两处：

1. **决策 → 设计规格。** 将问题、结论和理由写入正在讨论的设计规格，即 brainstorming 技能产出的持久设计文档，位置遵循宿主项目存放这类文档的约定；尚无规格时 → 结论仍 MUST 写入宿主的设计文档。
2. **原型 → 一次性分支。** 将原型本身提交到名称清晰的一次性分支，作为决策背后的原始依据；变体、切换器和终端外壳不进入主干分支。
