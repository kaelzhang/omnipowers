# 调研

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 何时使用

任务是通过调查回答问题，而非构建产物 → 你 MUST 应用本技能，无论来源位于网络、已安装的软件包还是本地代码库。

## 铁律

```
每条声明都追溯到对它负责的一手来源
```

- 调研时 → 你 MUST 将每条声明追溯到对它**负责**的来源：官方文档、规格或标准、源代码本身、项目的变更日志或发布说明，或你运行并记录的基准测试/实验。
- 能访问负责这条声明的来源 → 你 MUST NOT 将转述 — 博客文章、Stack Overflow 回答、教程或 AI 总结 — 作为声明的权威依据。
- 寻找对声明负责的来源时 → 二手来源 MAY 指路：用它找到一手来源，再到那里验证声明并引用一手来源。

## 输出约定

确定的问题 — 准确的提问内容，包括版本/日期约束。

- 交付调研发现项时 → 发现项 MUST 写入单个 Markdown 文件。
- 用于确定决策的调研 — `design-docs` 产物，按 `using-omnipowers` 解析位置，回退路径为 `docs/research/YYYY-MM-DD-<topic>.md`。
- 声明出现在发现项文件中 → 它 MUST 在行内附带引用：链接（来源有版本或易变时附版本或检索日期）、源代码的 `file:line` 引用，或你实际测量所用的命令和环境。
- 声明没有引用 → 它 MUST NOT 作为发现项呈现；验证它、移入明确标注未验证的线索部分，或删除它。
- 交付发现项文件时 → 文件 MUST 在开头附近直接回答确定的问题，再列出支撑细节。

## 来源冲突

- 来源互相矛盾 → 你 MUST 如实报告冲突：各来源的说法，以及各自的版本和日期。
- 来源互相矛盾 → 你 MUST NOT 悄悄选择一方作为答案来解决冲突。
- 来源互相矛盾 → 你 SHOULD 说明哪个来源更可能具有权威性及理由（版本较新、更接近实现）。

## 无法访问来源时

- 环境无法联网，或负责这条声明的来源因别的原因无法访问 → 发现项文件 MUST 醒目标明内容基于训练数据截止时的内置知识。
- 环境无法联网，或负责这条声明的来源因别的原因无法访问 → 每条相关声明 MUST 标注为未验证。
- 调研时 → 你 MUST NOT 将记忆内容作为已验证的调研呈现。

## 范围纪律

- 调研时 → 你 MUST 回答用户提出的问题 — 同一个问题、同一个范围。
- 用户未要求调查某条线索 → 你 MUST NOT 为追查它而扩大调查范围。

## 自我开脱 — 停止

| 借口 | 命令 |
|--------|---------|
| “博客比文档讲得更清楚” | 用它找到文档，再引用文档。 |
| “我已经知道答案” | 向负责这条声明的来源验证，或标注为未验证的记忆。 |
| “这个相邻话题显然相关” | 放入线索部分。 |
| “最后再加引用” | 验证当下就记录引用。 |

## 危险信号 — 停止并重新验证

| 危险信号 | 命令 |
|---|---|
| 能访问官方文档，声明却引用博客/SO/AI 总结 | 将声明追溯到负责这条声明的来源。 |
| 未打开任何来源就写下发现项 | 验证每条声明或逐条标注。 |
| 用户只问了一个问题，发现项文件却回答了三个 | 缩回原问题的范围；剩余内容移入线索部分。 |
