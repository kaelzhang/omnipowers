# 设计两次 — 用约束区分替代方案

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 用约束区分

在 `brainstorming` 中产出替代设计时 → 你 MUST 用约束区分各次尝试，为每次尝试分配一个设计约束，各约束彼此正交。

## 第 1 步 — 写下共享问题陈述

- 产出任何设计前 → 你 MUST 写下各次尝试共享的问题陈述：模块要完成什么、调用方是谁、外部硬约束是什么。
- 编写共享问题陈述时 → 陈述 MUST NOT 包含候选设计、草图或倾向方向。

## 第 2 步 — 独立产出设计

产出替代方案时 → 你 MUST 产出两个设计，每个设计对应一个约束。

存在第三个正交约束 → 你 MAY 增加第三个设计。

产出每个设计时 → 设计 MUST 交付：

1. 接口本身 — 入口、签名、不变量、错误模式；
2. 一个调用方用法示例；
3. 实现在接口背后隐藏的内容。

- subagent 收到设计任务时 → 每个 subagent MUST 只收到共享问题陈述和自己的约束，不接收共享草稿、其他 subagent 的输出或你的倾向提示。
- 宿主没有 subagent，且你正在产出第二个设计 → 你 MUST NOT 编辑第一个设计。
- 宿主没有 subagent，且第一个设计已写在页面上 → 第二个设计 MUST NOT 仅据此沿用第一个设计的形式。

## 第 3 步 — 比较接口

深度 — 每个入口相对于接口规模所隐藏的行为量。

删除测试 — 按接口契约重写实现时，能否在不改调用方的情况下更换数据结构和算法，还是要复刻原有内部实现。

变更局部性 — 接口能否将预期变更限制在边界内，还是会将变更扩散到调用方。

比较设计时 → 你 MUST 只比较接口。

**接口标准** — 上文定义的深度、删除测试和变更局部性。

设计的实现优雅但接口很浅时 → 实现 MUST NOT 成为挽救接口的理由。

## 第 4 步 — 综合并交还

- 选择结果时 → 你 MUST 选出胜者，并逐项说明胜出的理由。
- 次优设计中最好的一个想法能改进胜出设计的结构时 → 胜出设计 MAY 吸收这个想法。
- 综合设计时 → 你 MUST NOT 将设计折中成一个不满足任何约束的方案。
