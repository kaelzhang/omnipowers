# 头脑风暴

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 闸门

```
用一行陈述目标和交付标准，否则先确定两者
```

写代码前 → 你 MUST 能用一行陈述工作要达成什么，以及完成时能观察到什么条件，并确信用户认同两者。

你能陈述两者，且下方四类用户决策均不适用 → 你 MUST NOT 请求许可、设计评审或计划批准。

## 用户决策

用户决策 — 目标和交付标准；你无法解决的阻塞项；严重风险；对请求的分歧。

严重风险 — 工作会破坏现有契约、丢失数据、难以逆转，或带来用户尚未了解的成本。

对请求的分歧 — 已验证的项目事实与请求矛盾：能力已存在、所述假设不成立，或存在明显更好的路径。

四类用户决策中有一类适用 → 你 MUST 与用户确定这项决策。

- 目标或交付标准不清楚，或依赖你的假设 → 你 MUST 在构建前与用户确定。
- 阻塞项无法解决 → 你 MUST 连同建议的变通方案一起呈现，并且你 MUST 在采用变通方案前获得批准。
- 存在严重风险 → 你 MUST 说明风险、后果和建议。
- 对请求存在分歧 → 你 MUST 说明验证了什么、验证位置以及替代方案。

呈现四类用户决策中的任一类时 → 你 MUST 使用 `confirming-with-the-user` 技能。

## 排除的问题

头脑风暴期间 → 你 MUST NOT 向用户询问：

- 如何完成工作：方法、架构、拆分、库、文件布局或步骤顺序；
- 何时执行：先后次序、分阶段安排或先做什么；
- 对已确定目标的继续执行许可；
- 你能自行确定的内容；
- 已作出的决策；
- 有明显默认选项、可逆且影响轻微的选择。

## 最佳实践

选择方法时 → 你 MUST 选择本领域合格从业者会采用的方法，以项目所在行业的成熟实践为依据，并符合项目现有范式和约定。

- 没有成熟模式、选择的约束超出本次工作或难以逆转，且你无法确信地说出现行实践 → 你 MUST 在确定前通过权威来源验证。
- 决策要经过权威验证 → 记忆 MUST NOT 成为决策依据。
- 成熟领域的日常工作涉及你已能回答的问题 → 你 MUST NOT 花用户的时间研究。
- 能力可能已存在 → 你 MUST 在构建前按领域概念搜索代码库，不只按关键词搜索。
- 设计与已记录的项目决策矛盾 → 你 MUST 指出矛盾，不默默覆盖原决策。
- 请求跨越多个独立子系统 → 你 MUST 在开始前说明范围并拆分。
- 方法实现更快、测试更容易或能避开沟通 → 你 MUST NOT 据此选择。
- 交付工作时 → 你 MUST NOT 将缩水版本当作目标呈现。
- 你明知采用了捷径 → 你 MUST 在交付消息中告知用户。

设计围绕模块接口展开，且替代方案并不明显 → 读 `@design-it-twice.md` 并照做，再确定方案。

推理和研究无法解决设计问题 → 你 MAY 按 `prototyping` 技能的完整规则构建一次性原型来回答。

## 目标记录

目标记录 — 已确定的目标和交付标准，产物角色为 `design-docs`，位置按 `using-omnipowers` 解析，回退路径为 `docs/design/YYYY-MM-DD-<topic>.md`。

你能独立陈述目标，且工作在本轮完成 → 你 MUST NOT 为此创建文档。

构建前 → 你 MUST NOT 等待他人评审或批准目标记录。

目标记录已写好 → 你 MUST NOT 再次评审。
