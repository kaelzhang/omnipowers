# 深化浅模块

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 先分类每个依赖

深化一组浅模块前 → 你 MUST 将最终模块的每个依赖归入以下四类中的一类。

### 1. 进程内

**进程内依赖** — 纯计算和内存状态，没有 I/O。

### 2. 可在本地替代

**可在本地替代的依赖** — 真实基础设施，存在能忠实还原行为、在测试套件中运行的本地替代品。

存在本地替代品 → 你 MUST NOT 仅为测试而将依赖暴露为模块接口上的端口。

### 3. 远程但自有

**远程但自有的依赖** — 宿主项目通过网络访问的自有服务。

### 4. 真正的外部依赖

**真正的外部依赖** — 宿主项目无法控制的第三方服务。

依赖是真正的外部依赖 → 深化后的模块 MUST 通过注入端口接收依赖。

## 接缝纪律

- 组织实现时 → 实现 MAY 保留私有内部接缝。
- 测试使用私有内部接缝很方便 → 这些接缝 MUST NOT 据此通过接口暴露。

## 测试迁移：替换

深化过程吸收浅模块时 → 你 MUST 按顺序执行以下步骤，替换与实现耦合的测试：

1. 先写接口级测试；通过深化后模块的接口覆盖旧测试保护的相同可观察行为；断言调用方能看到的结果，不断言内部状态。
2. 将旧测试套件作为检查清单逐项检查，验证覆盖范围等价；保留两套测试，直到旧套件保护的每个行为都经过接口测试。
3. 验证覆盖范围等价后 → 删除与实现耦合的测试。
