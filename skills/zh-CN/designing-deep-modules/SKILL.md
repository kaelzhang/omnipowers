# 设计深模块

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 术语

讨论或记录设计时 → 你 MUST 按以下含义使用这些术语：

- **模块** — 有接口和实现的任何单元：函数、类、包或服务。
- **接口** — 调用方正确使用模块要知道的全部内容，包含模块未明说的要求，不只类型签名。
- **深度** — 调用方每学习一单位接口就能使用的行为量。
- **深模块** — 接口小、背后承载大量行为的模块。
- **浅模块** — 接口复杂度接近实现复杂度的模块。
- **接缝** — 模块接口所在的位置，实现能在这里变化而不改调用方。

## 删除测试

接受任何新建或重塑的模块前 → 你 MUST 执行删除测试：设想删除模块，再重读调用方。

- 删除模块后，调用方仍使用相同部件或只需向下一层调用 → 你 MUST 深化模块（将真实行为移入内部）或移除模块（内联）。

## 双适配器规则

- **有充分依据的抽象** — 至少有两个实现满足当前真实需求的抽象：第二个生产变体，或为无法在测试中运行的依赖提供的真实测试适配器。
- 引入接口、端口或抽象层时 → 你 MUST NOT 只给它一个有充分依据的实现。

## 接口包含调用方要知道的全部内容

对于设计的每个模块 → 你 MUST 枚举完整接口：

- **不变量** — 模块保证什么，以及要求调用方维持什么。
- **错误模式** — 什么会失败、如何报告失败、失败后保留什么状态。
- **顺序约束** — 哪个调用先于哪个调用；哪些调用不能重复。
- **所需配置** — 调用方要提供的设置、环境和接线。
- **性能预期** — 调用方能依赖的复杂度、阻塞行为、缓存和分配模式。

枚举后发现契约庞大而实现单薄时 → 你 MUST 重新设计模块，不靠文档绕过问题。

## 从结构上保障可测试性

- 设计模块时 → 你 MUST 能仅通过接口测试行为。
- 测试模块要越过接口访问内部 → 你 MUST 重塑模块，不为测试撬开内部。
- 测试模块时 → 测试 MUST 通过接口断言可观察结果，不断言内部状态。
- 组织深实现时 → 你 MAY 使用带有内部接缝的更小私有部件。
- 测试使用内部接缝很方便 → 这些接缝 MUST NOT 据此提升为接口。
- 设计模块时 → 你 SHOULD 接收依赖，不在内部构造依赖。
- 设计模块时 → 你 SHOULD 返回结果，不修改共享状态。

## 深化现有浅模块

重组现有代码，包括将一组薄包装合并为一个深模块、决定如何处理深化后模块的依赖（数据库、自有远程服务、第三方 API），或迁移旧测试时 → 读 `@deepening.md` 并照做。

## 危险信号 — 停下

以下任一项成立 → 你 MUST 重做设计：

- 模块的方法大多委托给下一层形式相同的方法。
- 接口操作数与实现函数数大致相等。
- 接口、trait 或端口只有一个实现，且看不到具体的第二个实现。
- 以“保持分层整洁”为由添加包装，却不提供行为。
- 测试导入模块内部，而非接口。
- 调用方要阅读模块源码才能正确使用，包括未明说的不变量、顺序或错误模式。
- 你无法用一句话说明模块的存在给调用方带来什么。

## 检查清单

宣称模块设计完成前 → 你 MUST 能勾选每一项：

- [ ] 已执行删除测试，没有残留透传模块
- [ ] 每个抽象至少有两个有充分依据的实现
- [ ] 已枚举完整接口：不变量、错误模式、顺序、配置、性能
- [ ] 仅通过接口就能测试行为
- [ ] 用一句话说明每个模块给调用方带来什么
