# 代码异味基线 — code-auditing

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 总则

- 宿主项目的书面标准（编码标准文档、贡献指南、风格指南、lint 或 formatter 配置）与本基线冲突 → 你 MUST 忽略冲突的异味。
- 匹配某种异味 → 你 SHOULD 标记匹配项。
- 标记了异味 → 标记 MUST 写明异味名称及具体理由。
- 匹配某种异味 → 你 MUST NOT 仅凭异味本身就将它报告为缺陷、违规或 Critical 问题。
- 宿主工具能检测或自动修复某种异味 → 你 SHOULD 跳过此异味。

## 基线

基线条目 — 下表中的异味定义及修复方向参考。

| 异味 | 定义 | 修复方向 |
|---|---|---|
| **过长函数** | 单个函数承担多项职责，只有借助内部注释或空行划分的“段落”才能读懂。 | 将每个步骤提取为独立函数，以表达意图的名称命名。 |
| **重复逻辑块** | 相同逻辑结构出现在两处或更多位置，每次改动都要同步修改各处才能保持正确。 | 将共享逻辑结构统一提取，供各处调用。 |
| **依恋情结** | 函数主要操作另一个模块的数据，而非自身数据。 | 将函数移到它反复访问的数据附近。 |
| **基本类型偏执** | 用裸字符串、数字或布尔值表示真实领域概念（ID、金额、范围、状态）。 | 为概念及规则定义专用类型。 |
| **霰弹式修改** | 一次逻辑改动迫使多个文件中分散的小块代码一起修改。 | 将共同变化的部分集中到一个模块。 |
| **发散式变化** | 一个模块因多种无关原因反复修改。 | 拆为多个模块，每个模块只因一个原因变化。 |
| **数据泥团** | 同一组字段或参数总是一起出现。 | 组合成一个具名类型，替代字段或参数传递。 |
| **过长参数列表** | 参数数量导致调用点难读或容易错位。 | 将相关参数组成对象，或由被调用方推导。 |
| **推测式泛化** | 为尚无使用者的未来需求建立抽象、钩子或参数。 | 删除，等真实的第二个用途出现时再引入。 |
| **消息链** | 调用方沿 `a.b().c().d()` 访问，与结构中的每个环节耦合。 | 在调用方已持有的对象上，用一个方法封装访问过程。 |
| **不当亲密** | 两个模块相互读取或操纵内部细节。 | 定义显式接口，或将纠缠的部分放到一起。 |
| **死代码** | 没有执行路径能到达的代码——未使用的函数、未引用的分支、注释掉的代码块。 | 删除。 |

## 报告格式

标记了异味 → 标记 MUST 包含三部分：异味名称、diff 中的证据（文件与行号），以及表中的修复方向；修复方向仅作建议，不作硬性要求。
