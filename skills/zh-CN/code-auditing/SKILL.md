# 代码审计

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 定义

检查点评审 — 工作推进前，对已完成工作开展的独立评审，以工作要求和评审者简报为依据。

标准审计 — 依据宿主项目检查清单开展的评估。

标准来源 — 按 `using-omnipowers` 解析的宿主 `standards` 产物；第 3 步指项目已发布且要求贡献者遵循的标准集；第 4 步指没有已发布的标准。

审计报告 — `records` 产物，位置按 `using-omnipowers` 解析，回退路径为：

```
<project-root>/.omnipowers/reviews/<YYYY-MM-DD>-<HHMMSS>-<review-target>.md
```

`<project-root>` — 仓库根目录；位于仓库外时指工作目录。

`<review-target>` — 简短的 kebab-case 标识，表示评审对象。

## 总则

- 声称代码已评审前 → 你 MUST NOT 在完成对真实代码的独立检查并为每个发现项提供证据前，声称代码已评审。
- 本技能创建的每个产物 → 产物 MUST 存放在被审计项目内，采用项目声明的位置（回退路径：`<project-root>/.omnipowers/`）。
- 使用本技能时 → 本技能 MUST NOT 依赖被审计项目以外的任何工具、服务或仓库。

## 使用时机

未完成计划内的单个任务完成 — 不触发评审。

以下任一条件成立时 → 你 MUST 使用本技能：

- 计划、主要功能或复杂 bug 修复已完成；
- 工作即将合并、创建 pull request、发布、交接、成为依赖或进入重构；
- 用户要求审计或评估代码库、PR、diff 或提交范围；
- 工作陷入僵局，重新审视能帮助推进。

评审条件已满足 → 你 MUST NOT 以改动“简单”“小”或“显然能用”为由跳过评审或敷衍评审。

## 阶段 1 — 分流：检查点评审或标准审计

已完成的分支有项目检查清单 → 你 MUST 执行检查点评审，并用检查清单补充检查视角。

### 1a. 检查点评审

开展检查点评审时 → 评审范围 MUST 覆盖整项工作，而非仅覆盖最后一次提交：

```bash
BASE_SHA=$(git merge-base HEAD <main-branch>)   # feature / pre-merge review
HEAD_SHA=$(git rev-parse HEAD)
```

- 评审不是恰好只有一次提交的单任务检查点 → 你 MUST NOT 使用 `BASE_SHA=$(git rev-parse HEAD~1)`。
- 开展检查点评审时 → 你 MUST 评审已提交的范围。
- 开展检查点评审时 → 你 MUST 对照工作原定目标开展评审。
- 没有要求来源 → 你 MUST 明确声明本次评审没有要求来源（仅评估质量维度，属于降级评审）。

#### 独立检查（检查点评审）

检查点评审 → 读 @reviewer-brief.md 并照做。

- 有可用 subagent → 你 MUST 填好简报中的占位符，并用简报派发一名独立评审者。
- 已派发独立评审者 → 评审者 MUST 只读运行。
- 没有可用 subagent → 你 MUST 自行开展一次刻意分开的评审：将 diff 视为他人所写，只依据要求和 diff 工作（绝不依据编写时的记忆），得出结论前从头到尾读完整个 diff，应用完整简报，并保持只读（先记录发现项；到阶段 4 再行动）。
- 使用无 subagent 的回退方式 → 你 MUST NOT 走过场。

### 1b. 标准审计

- 标准来源第 1、2 或 3 步适用 → 你 MUST 依据对应来源开展审计。
- 标准来源第 1、2 或 3 步适用 → 你 MUST NOT 自行生成检查清单。
- 已发布来源未覆盖下列某个检查清单维度 → 你 MAY 依据 `@code-smells.md` 中的可移植基线审计此维度。
- 对未覆盖的维度使用了可移植基线 → 你 MUST 在报告中说明。

标准来源第 4 步适用 → 你 MUST 在审计任何内容前按以下步骤生成检查清单：

1. 调查项目：阅读足够的项目内容，让检查清单立足于代码库，覆盖语言、框架、架构与分层、业务领域、安全 / 信任涉及的范围、并发模型、数据与 schema、构建与发布、测试设置，以及项目自身约定（`CLAUDE.md` / `AGENTS.md` / 文档 / linter）。
2. 起草适配项目的多维检查清单；若项目没有某个维度适用的代码或行为，删除此维度并说明原因。
3. 在有限轮次内迭代优化：至少采用三种不同视角——完整性 / 遗漏的失效模式、项目适配度 / 可执行性、冗余 / 粒度——每个视角单独一轮；仅在上一轮仍发现真实缺口时再进行一轮；遇到首个未产生实质改动的轮次就停止。
4. 写入解析后的 `standards` 位置；项目未声明位置时，回退到 `<project-root>/.omnipowers/rules/CODE_AUDITING.md`；添加简短页头（项目、生成日期、维度列表），并按维度分组。
5. 展示检查清单和解析后的位置，纳入用户修改并获得批准后，再依据清单开展审计。

- 生成检查清单时 → 清单 MUST 至少覆盖以下维度，且每个维度都适配当前项目：正确性与逻辑；安全与信任边界；错误处理与失效模式；并发、顺序与资源生命周期；性能与复杂度；API / 契约 / 向后兼容；数据、schema 与迁移；测试与覆盖率（包括每个已修复 bug 的回归测试）；可读性、命名与可维护性；结构、分层与边界；依赖与供应链；文档与注释。
- 对生成的每个检查清单条目 → 条目 MUST 是具体、可检查的问题，绝非含糊的“好不好？”。
- 优化生成的检查清单时 → 你 MUST NOT 超过 **5** 轮。
- 首次使用生成的检查清单前 → 你 MUST 展示清单和解析后的位置，纳入用户修改并获得批准后，再依据清单开展审计。
- 对生成的检查清单 → 你 SHOULD 将它视为值得提交的项目产物。
- 已有生成的检查清单 → 你 MUST 原样使用清单开展本次审计。
- 已有生成的检查清单 → 你 MUST NOT 在审计中途重写清单。
- 开展改动审计时 → 你 MUST NOT 逐行重新审计无关代码。

## 阶段 2 — 严格检查（两种模式）

对每个检查对象 → 你 MUST：

- 检查真实代码——阅读代码，不作假设；
- 给出结论——**pass**、**fail**、**concern** 或 **n/a**，结论为 n/a 时用一行说明原因；
- 对每个 `fail` / `concern`，记录具体的 `file:line`、证据、**严重程度**以及具体、可执行的修复方案；
- 对照真实代码验证每个发现项，不提出推测性的发现项；无法验证时，说明并标记为未验证；
- 应用 YAGNI 并结合上下文——标记“缺少 X”前，确认 X 确有需求；标记某种模式前，检查是否存在历史遗留 / 兼容性 / 有意采用的原因；
- 跳过项目工具已强制检查的内容（linter、formatter、type checker）；
- 具体陈述问题和修复方案，不作表演，不加赞美或填充文字。

对每个发现项 → 你 MUST NOT 在规格符合度和代码质量两个维度间调整它的等级。

## 阶段 3 — 记录审计

- 开展标准审计、全项目或子系统评估、发布前评审，或用户要求存档的审计 → 书面文件是 REQUIRED 的。
- 对即将合并的改动开展检查点评审 → 报告文件是 OPTIONAL 的。
- 对每次审计 → 报告 MUST 包含对象和范围（检查点评审还包括评审的提交范围）、要求或检查清单引用、每项结论、全部发现项（每项包含 `file:line` + 严重程度 + 修复方案）以及总体评估。

## 阶段 4 — 报告并行动

- 对每次审计 → 你 MUST 在会话中输出简短摘要：按维度和严重程度分组的发现项、每个 `Critical` 和 `Important` 发现项（位置 + 一行修复方案），以及总体评估（交付 / 先修复 / 返工）。
- 在每种模式下 → 会话摘要是 REQUIRED 的。
- 阶段 3 要求书面记录 → 摘要 MUST 包含记录路径。
- 对象是 pull request 且你向它发布发现项 → 你 SHOULD 将每个行内发现项放入对应代码评论线程，而非合并为一条顶层评论。
- 发现项为 **Critical** → 你 MUST 在继续前修复。
- 发现项为 **Important** → 你 MUST 在任何后续实现工作（下个任务、重构或合并）前修复。
- 发现项为 **Minor** → 你 MUST 将它记录到任务笔记或 issue tracker。
- 发现项有误 → 你 MUST 引用代码、测试或要求，以具体技术理由提出异议。
- 发现项不正确 → 你 MUST NOT 只为结案而接受。
- 发现项有误 → 你 MUST NOT 在未引用代码、测试或要求并给出具体技术理由时直接驳回。

## 阶段 5 — 演进检查清单（有闸门；标准审计）

- 使用或创建检查清单的审计结束后 → 你 MUST 评估清单是否要修改，并提出**范围明确**的修改建议。
- 用户尚未批准对 `CODE_AUDITING.md` 的修改 → 你 MUST NOT 修改它。
- 检查清单漏掉真实缺陷 → 此缺陷 MUST 转为**新增条目提案**。
- 某类发现项在多次审计中反复出现 → 你 MUST 提议提升它的等级（提高严重程度，或升级为项目硬性规则）。
- 某条目产生误报或无法执行 → 你 MUST 提议修订此条目。

## 严重程度

Critical — 破坏正确性、安全性或数据完整性的发现项。

Important — 构成真实缺陷或风险的发现项。

Minor — 涉及风格、清晰度或非紧急改进的发现项。

- 发现项为 Critical → 你 MUST 在交付前修复。
- 发现项为 Important → 你 MUST 在后续实现工作前修复。
- 发现项为 Minor → 你 MAY 延后处理。
- 发现项为 Minor → 你 MUST 记录。

## 危险信号 — 停止

| 危险信号 | 改为这样做 |
| --- | --- |
| “我再读一遍自己的推理就行。” | 执行 1a 的独立检查。 |
| “这里没有 subagent，就跳过吧。” | 执行无 subagent 的回退检查。 |
| “我边评审边修改。” | 保持检查只读；到阶段 4 再行动。 |
| “这个 Critical 问题大概没事。” | 继续前修复。 |
| “Important 问题以后再修。” | 在任何后续实现工作前修复。 |
| 发现项没有 `file:line` 证据 | 在代码中验证，或标记为未验证。 |

## 自我开脱 — 全部驳回

| 自我开脱 | 改为这样做 |
| --- | --- |
| “写的时候我已经检查过了。” / “我是作者，我知道它正确。” | 将已完成的 diff 视为陌生代码，单独开展一轮评审。 |
| “Minor 问题无关紧要，略过。” | 记录每个 Minor 问题。 |
| “检查清单差不多，边查边改吧。” | 在阶段 5 提议修改；你 MUST NOT 在审计中途重写清单。 |
