# 对计划做压力测试

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 定义

- 计划压力测试 — 持续拷问用户的计划。
- 拷问结束 — 用户确认双方对计划形态、取舍以及每个分支作出的决策的理解一致。
- 决策树 — 以计划中明确或隐含的选择为节点，以备选项、风险和后果为分支。

## 使用时机

- 用户要求拷问计划、想法或决策，且未必打算构建 → 你 MUST 使用本技能。
- 你准备构建任何内容 → 你 MUST NOT 用本技能绕过 brainstorming 技能在编码前确定目标和交付标准的闸门。

## 拷问循环

- 拷问时 → 你 MUST 覆盖决策树的每个分支：目标、假设、备选方案、风险、失败模式和边界情况，包括用户尚未考虑的分支。
- 提出依赖上级决策的问题前 → 你 MUST 先确定上级决策。
- 提问时 → 你 MUST 只问一个问题，然后等待用户答复，再问下一个。
- 提问时 → 你 MUST 附上你会给出的答案，并用一行说明理由。
- 某项事实能从环境（代码库、文档、命令或搜索）获取 → 你 MUST 自行查证。
- 某项事实能从环境获取 → 你 MUST NOT 向用户询问。
- 决策权属于用户 → 你 MUST 交给用户决定。
- 决策权属于用户 → 你 MUST NOT 自行假定或静默决定。
- 呈现问题时 → 你 MUST 遵循 confirming-with-the-user 技能：用直白语言，选项可枚举时给选项标号，说明每项的影响，并给出推荐。

## 终止状态

- 使用本技能期间 → 你 MUST NOT 产出新的规格、设计文档、计划文件、笔记文件或任何其他产物。
- 拷问改变了项目已有记录的决策 → 这份记录 MUST 在拷问结束后更新，绝不在拷问过程中更新。

## 交接

- 用户决定构建计划的任何部分，包括要求书面规格或设计 → 你 MUST 交接给 brainstorming 技能，此后由它的目标闸门约束。
- 计划经过拷问 → 你 MUST NOT 把它当作已确定的目标。

## 自我开脱 — 不接受

- “用户是专家 — 不用给推荐” → 给出推荐是 REQUIRED 的。
