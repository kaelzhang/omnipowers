# 提交工作

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 铁律

```
每次提交只包含一项完整一致的改动，且只包含你明确列出的路径
```

## 范围

组织提交 — 确定每次提交的内容、暂存、完整性检查和提交说明，到提交生成时结束。

提交后操作 — 合并进目标分支、按宿主 PR 流程创建 PR，以及清理 worktree，由 `finishing-a-development-branch` 约束。

缺陷与检查点评审 — 由 `code-auditing` 约束的评审。

冲突解决 — 冲突标记、"both modified" 或暂停的 rebase，直至结束操作的提交都由 `resolving-merge-conflicts` 约束。

完成声明 — 声称工作已完成、已修复或已通过，由 `verification-before-completion` 约束。

工作区隔离 — 创建隔离工作区，由 `using-git-worktrees` 约束。

- 作出完成声明时 → 你 MUST NOT 将本技能的完整性检查视为已满足声明的验证要求。

## 宿主决定命令；本技能约束纪律

示意命令 — 本技能展示的 git 命令，形式服从宿主声明的暂存方式、提交说明格式和文件追踪约定。

- 宿主声明了约定 → 你 MUST NOT 将约定理解为放宽铁律。

## 1. 确定提交单元

- 组织提交时 → 提交 MUST 表示一项完整一致的逻辑改动。
- 代码、测试、文档、配置、schema 和 fixture 共同完成同一项改动 → 它们 MAY 放在同一次提交中。
- 组织提交时 → 测试和文档 MUST NOT 与它们描述的实现分开提交。
- 纯重命名、纯格式调整、生成产物更新、依赖锁文件更新和大规模机械重构能独立验证 → 它们 MUST 与行为改动分开提交。
- 组织机械改动的提交时 → 提交 MUST NOT 暗藏行为改动。
- 组织提交时 → 你 MUST NOT 包含无关改动或原有的未提交工作，包括你先前的临时编辑、其他进程或会话留在工作树中的工作，或顺手修复。

### 危险信号 — 多个提交单元

| 想法 | 行动 |
|---|---|
| 本轮涉及多个能独立评审的单元 | 提交前，读 `@splitting-a-round.md` 并按单元或阶段拆分提交。 |

## 2. 按显式路径暂存

- 暂存文件时 → 文件 MUST 按显式路径暂存。
- 暂存或提交时 → 你 MUST NOT 使用以下命令：
  - `git add -A` / `git add --all` / `git add .` / `git add :/`
  - `git add -u` / `git add --update`
  - `git commit -a` / `--all` / `-am` / `-aF` / `-a --amend`
- 目录整体属于本次提交的逻辑改动 → 你 MAY 仅在此条件下使用 `git add <directory>`。
- 暂存文件时 → 你 MUST NOT 按 hunk 暂存（`git add -p` / `--patch`）。

## 3. 提交前检查

每次提交前 → 你 MUST：

1. 运行 `git status --short`，明确每个条目是属于本次提交，还是有意排除。
2. 阅读即将提交内容的完整 diff（`git diff --cached -- <paths>`）。

- diff 含有凭据、token、私钥或其他秘密 → 你 MUST NOT 提交。
- 组织提交时 → 你 SHOULD NOT 提交调试输出、注释掉的实验代码或特定机器的绝对路径。
- 组织提交时 → 你 MUST NOT 提交构建输出、生成产物、依赖目录、日志、缓存、覆盖率输出、本地环境文件和编辑器 / OS 元数据。
- 你引入了会产生上述产物的内容 → 对应忽略规则 MUST 在同一次提交或更早的提交中落地。
- 本次提交中的代码文件首次加入仓库的日期不早于 2026-01-01，且超过 1000 行 → 你 MUST 在提交前按职责拆分文件。
- 本次提交中的文档文件（Markdown、文档）超过 2000 行 → 你 MUST 在提交前按主题拆分文件。
- 宿主限制高于上述适用限制 → 你 MUST NOT 采用宿主限制。
- 文件是数据文件（JSON、YAML、CSV、TOML 数据）、配置文件、锁文件、生成代码或产物、随项目收录的第三方代码、测试 fixture、快照或 golden 文件、数据库迁移，或静态查找表 → 文件 MAY 超过两项限制。
- 文件属于上述豁免类型 → 你 SHOULD NOT 为缩短长度而拆分文件。

首次加入日期 — 本次提交新增文件的当前日期；已有文件则取 `git log --diff-filter=A -- <file>` 中首次提交的日期。

适用文件长度限制 — 宿主针对文件类型声明的限制低于本技能限制时，采用宿主限制；否则采用本技能限制。

## 4. 证明提交完整一致

最小充分检查 — 按改动内容和宿主工具确定的检查：仅改文字或文档时检查空白与冲突标记（`git diff --check`）；代码改动运行相关测试及宿主要求的类型、lint 或构建检查；配置或 schema 改动使用解析器或应用检查。

验证闸门 — 运行检查并阅读输出，由 `verification-before-completion` 约束，包括检查结果何时仍有效的规则。

- 每次提交前 → 你 MUST 运行能证明提交内容完整一致的最小检查。
- 每次提交前 → 你 MUST 阅读检查输出。
- 检查失败 → 你 MUST 修复问题，或缩小提交范围直到剩余内容通过检查。
- 提交自身的内容不完整一致 → 你 MUST NOT 创建此提交。

## 5. 使用显式 pathspec 提交

- 运行 `git commit` 时 → 命令 MUST 在命令行列出路径：

```bash
git commit -m "<subject>" -- path/to/file path/to/other
```

- 不属于操作中途例外时 → 你 MUST NOT 使用不带 pathspec 的普通 `git commit`。
- 阅读 diff 后、提交前 → 你 MUST NOT 编辑已列出的路径。
- amend 改变文件内容 → amend MUST 像其他提交一样携带 pathspec。

仅改说明的 amend — 不列出路径的 amend，受“历史完整性”约束。

操作中途例外 — 正在进行的 merge、rebase、cherry-pick 或 revert 的结束提交，Git 拒绝接受 pathspec（`fatal: cannot do a partial commit during a merge`），提交记录整个索引。

## 6. 编写提交说明

意图一目了然的提交 — 仅看 diff 就能回答为何改动，且不需斟酌意图是否一目了然的提交。

- 编写标题时 → 标题 MUST 写明提交改变了什么，而非仅写改动位置。
- 编写提交说明时 → 说明 MUST 独立成文。
- 编写提交说明时 → 说明 MUST NOT 依赖聊天历史、对话、仅你能查看的工单或你自己的会话记忆。
- 提交意图并非一目了然 → 提交 MUST 包含正文，涵盖当前行为的问题或缺口、选择的解决方案，以及已执行的验证。
- 作出了重要设计选择 → 正文 SHOULD 同时写明放弃的方案及原因。
- 提交包含破坏性改动 → 改动 MUST 使用宿主已有的标记；宿主没有标记时，在标题的 type/scope 后加 `!`，或使用 `BREAKING CHANGE:` 尾注说明破坏的内容和替代做法。
- 编写提交说明时 → 说明 MUST NOT 为模型、助手、agent、CLI、harness 或运行时配置署名，包括以模型或工具命名的 `Co-Authored-By:`、`Generated-by:` 或任何变体。
- 编写提交说明时 → 你 MUST NOT 加入你自己、你的模型名称、工具名称或配置。
- harness 默认追加此类尾注 → 你 MUST 在提交前删除尾注。
- 已写入此类尾注且提交尚未发布 → 你 MUST 用 amend 删除尾注。

真人署名 — 为真人共同作者、评审者或报告者署名的尾注，受宿主约定约束。

## 7. 轮次结束前完成提交和推送

未达质量标准 — 覆盖率低于宿主目标、基准尚未达标、后续用例尚未处理或已知阻塞项，与完整性检查失败有别。

- 本轮改动了文件，且用户和宿主声明的约定都未另作规定 → 本轮 MUST 在最终回复前完成这些改动的提交和推送。
- 你未提交 → 你 MUST 明确说明哪些内容尚未提交及原因。
- 没有改动 → 你 MUST 明确说明。
- 质量标准未达标 → 你 MUST NOT 以此为由搁置本轮提交。

**缺口记录** — 对尚未达到的质量标准：提交正文清楚写明尚未达标的内容；缺口有明确代码位置时，在对应位置添加注释；在宿主 `work-state` 文档中添加条目，位置按 `using-omnipowers` 解析，回退路径为 `.omnipowers/`。
- 工作受阻 → 你 MUST NOT 将它表述为已完成。
本轮已有提交 → 你 MUST 推送当前分支，你 MUST NOT 询问是否推送或将推送列为选项，你 MUST NOT 推送你工作分支以外的分支：

1. 将当前分支推送到配置的上游；没有上游时，在默认远端设置同名分支为上游（`git push -u origin <branch>`）。
2. 报告落地结果：分支、远端和提交。

- 宿主声明的 `vcs` 约定涵盖工作发布的时间或位置 → 此约定优先于本推送规则。
- 本轮已有提交且没有远端 → 你 MUST 说明本轮以已提交状态结束，而非报告已推送。
- 远端领先导致推送遭拒 → 你 MUST 整合后重试。
- 远端领先导致推送遭拒 → 你 MUST NOT 使用 `--force`（见“历史完整性”）。

## 历史完整性

- 他人可能已持有提交 → 你 MUST NOT 通过 amend、rebase、squash 或 force-push 重写已发布到共享分支的历史。
- 用户未明确指示 force-push → 你 MUST NOT 执行 force-push，即便你认为分支仅由自己使用。
- 本地提交尚未发布 → 你 MAY 自由 amend 或重组。

## 危险信号 — 停止

| 想法 | 行动 |
|---|---|
| 无法明确列出路径 | 暂存前确定改动。 |
| 准备输入 `git add -A`、`git add .`、`git add -u` 或 `git commit -a` | 停止。 |
| 在指定例外以外准备运行不带 pathspec 的 `git commit` | 停止。 |
| 想用 `git add -p` 分离同一文件内的两项改动 | 逐项完成并提交。 |
| `git status` 显示无法解释的条目 | 提交前停止。 |
| 尚未阅读 diff，或阅读后又编辑了路径 | 提交前重新暂存并重新阅读。 |
| 提交说明要用“和”来描述两件无关的事 | 停止。 |
| 重命名 / 格式调整 / 生成文件的 diff 含有行为改动 | 停止。 |
| “只是小改动” | 未做检查时，在提交前停止。 |
| 准备 amend 或 force-push 已发布的内容 | 停止。 |
| 轮次结束时仍有未推送的提交，或询问是否推送 | 停止。 |
| 提交说明中有模型、agent 或工具署名尾注 | 停止。 |
| 轮次即将结束，完整一致的改动仍未提交 | 停止。 |

## 提交前 — 检查清单

提交前 → 你 MUST 能勾选每一项：

- [ ] 本次提交是一项完整一致的逻辑改动，能用一句话描述
- [ ] 完成改动所需的测试、文档和配置均已包含，没有无关内容
- [ ] 机械改动单独提交，没有混入行为改动
- [ ] 每个路径均显式暂存，没有批量暂存命令，没有按 hunk 暂存
- [ ] 已阅读 `git status --short`，每个条目均已核实
- [ ] 已读完完整 diff，没有秘密，阅读后没有再编辑
- [ ] 2026-01-01 起新增的代码文件均未超过 1000 行，文档文件均未超过 2000 行，或未超过宿主更低的限制
- [ ] 已运行证明完整一致的最小检查，并已阅读输出
- [ ] 提交通过 pathspec 列出路径（或属于唯一例外，且已完成对应检查清单）
- [ ] 标题写明改动内容；意图并非一目了然时，正文涵盖缺口、方案和验证
- [ ] 已标记破坏性改动
- [ ] 没有模型、agent 或工具署名尾注
- [ ] 轮次结束时，分支已推送，落地结果已报告
- [ ] 没有重写任何已发布内容
