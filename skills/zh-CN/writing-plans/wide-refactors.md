# 大范围重构——扩展—收缩

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 范围

大范围重构——一次机械变更（共享符号重命名、签名变更、模块迁移，或调用方迁移到替代 API），影响范围超出一个能独立评审和测试的任务所能容纳的范围。

影响范围——变更会破坏的调用点集合。

所有调用点都能放进一个大小合适的任务——一份评审者能把关的 diff、一个测试周期、一次提交 → 你 MUST 将重构规划为一个普通任务，且 MUST NOT 应用本文件。

## 全绿不变量

- 序列中每个任务结束后 → 代码库 MUST 能构建，且完整测试集 MUST 通过。
- 对每个任务 → 验证步骤 MUST 运行**完整**测试集，而非仅运行改动文件附近的测试。

## 排序——三个阶段

### 1. EXPAND——在旧形式旁引入新形式

- 规划 EXPAND 时 → 你 MUST 在旧形式旁加入新形式，两者都能完整工作。
- 规划 EXPAND 时 → 两种形式中的一种 MUST 委托另一种，行为只定义一次。
- 规划 EXPAND 时 → 本任务 MUST NOT 改动任何调用方。
- 验证 EXPAND 时 → 本任务中新形式的测试 MUST 通过，所有现有测试（仍在使用旧形式）也同时通过。
- 安排重构顺序时 → EXPAND MUST 独立成为一个计划任务，且 MUST 阻塞每个迁移批次。

### 2. MIGRATE——分批迁移调用方

- 规划 MIGRATE 时 → 你 MUST 按包或目录将调用方分批，每批作为一起变更、一起评审的单位。
- 规划 MIGRATE 时 → 每个批次 MUST 独立成为一个计划任务。
- 确定迁移批次大小时 → 批次大小 SHOULD 随影响范围调整，让 diff 能放进一次评审和一个全新上下文窗口。
- EXPAND 完成后 → 迁移批次 MAY 按任意顺序执行或并行执行。
- 每个迁移批次结束时 → 批次 MUST 全绿（完整测试集），且 MUST 以提交结束。
- 规划迁移批次时 → 批次 MUST 只含机械变更。
- 规划迁移批次时 → 你 MUST NOT 混入行为变更、清理或无关修复。

### 3. CONTRACT——移除旧形式

- 规划 CONTRACT 时 → 你 MUST 仅在调用方数量为零时移除旧形式。
- 安排重构顺序时 → CONTRACT MUST 是最后一个任务，受每个迁移批次阻塞。
- 规划 CONTRACT 时 → 任务 MUST 用精确搜索命令验证调用方为零（按铁律，计划写明命令及预期空结果），再删除旧形式，再运行完整测试集确认全绿，最后提交。
- 旧形式属于宿主暂时无法破坏的已发布接口 → CONTRACT MAY 在标记弃用后延期，由宿主用户确认延期，并将移除工作记录为单独的后续计划。

## 降级——两种形式无法共存时

- 宿主无法同时保留两种形式 → 你 MUST 改用短期集成分支，维持相同的分批约束：相同任务序列——先做破坏性变更，再按包分批——每个任务都在集成分支上提交，并在**分支上**维持全绿不变量（每个任务后分支能构建且完整测试集全绿）。
- 将集成分支合入主干时 → 你 MUST 仅在迁移完成且分支全绿时合并。
- 迁移只完成了一部分 → 你 MUST NOT 合并。
- 使用集成分支时 → 分支 MUST 只保留短时间。
- 使用集成分支时 → 你 SHOULD 频繁与主干同步。
- 两种形式能共存 → 你 MUST NOT 使用集成分支。

## 映射到计划文档

| 计划任务 | 阶段 | 阻塞依赖 |
|---|---|---|
| 任务 N | EXPAND | 前置功能任务（若有） |
| 任务 N+1 … N+k | MIGRATE，每个任务一个批次 | 仅任务 N |
| 任务 N+k+1 | CONTRACT | 每个迁移批次 |
