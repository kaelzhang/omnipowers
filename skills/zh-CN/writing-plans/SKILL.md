# 编写计划

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 概览

- 编写计划时 → 你 MUST 面向这样的熟练开发者：对代码库毫无了解、品味存疑、几乎不了解工具集和问题领域，也不懂好的测试设计。
- 面向这位实现者 → 计划 MUST 提供代码库、工具集、问题领域和测试设计知识，不假设对方已经掌握。
- 对每份计划 → 计划 MUST 为每个任务记录实现者所需的全部内容：要动哪些文件、实际代码、实际测试、要查阅的文档，以及验证方法。
- 规划功能时 → 你 MUST 将整个功能分解为细小任务。
- 规划和执行全程 → DRY、YAGNI、TDD 和频繁提交均为 REQUIRED 的要求。
- 开始编写计划时 → 你 MUST 声明：“我正在使用 writing-plans 技能编写实现计划。”

## 铁律

- 对每个代码步骤 → 步骤 MUST 包含实际代码。
- 对每个测试步骤 → 步骤 MUST 包含实际测试。
- 对每个命令步骤 → 步骤 MUST 包含精确命令及预期输出。
- 无法写出某步骤的具体内容 → 你 MUST 先消除未知，再写这个步骤。
- 无法写出某步骤的具体内容 → 你 MUST NOT 把未知内容留作计划中的占位符。

## 计划存放位置

计划——`work-state` 产物，位置按 `using-omnipowers` 解析，回退路径为 `.omnipowers/plans/YYYY-MM-DD-<feature-name>.md`。
- 解析到第 1 或第 2 项 → 你 MUST NOT 询问。
- 父目录缺失 → 你 MUST 创建。
- 宿主已有计划文档 → 你 MUST 写入现有文档，而非在旁边另建。

## 范围检查

- 规格涵盖多个独立子系统 → 你 MUST 为每个子系统分别制定计划，且 MUST 向用户说明。
- 规格涵盖多个独立子系统 → 每份计划 MUST 独立产出能工作、能测试的软件。
- 规格涵盖多个独立子系统 → 你 MUST NOT 将它们捆进同一份计划。

## 文件结构

定义任何任务前 → 你 MUST 列清要创建或修改哪些文件，以及每个文件的职责。

- 对每个文件 → 文件 MUST 只有一个清晰职责，边界和接口明确。
- 文件大小限制——由 `committing-work` 负责的规则。
- 文件一起变化 → 它们 MUST 放在一起。
- 拆分文件时 → 你 MUST 按职责拆分，而非按技术层拆分。
- 在现有代码库中规划时 → 你 MUST 遵循现有模式。
- 现有代码库使用大文件 → 你 MUST NOT 擅自调整结构。
- 正在修改的文件已变得难以维护 → 你 MAY 在计划中加入对它的拆分。

对每个任务 → 任务 MUST 产出自包含、独立成立的变更。

## 确定任务大小

任务——具有独立测试周期，且值得由全新评审者把关的最小单位。

- 定义任务时 → 你 MUST 将准备、配置、脚手架和文档步骤并入依赖它们来交付的任务。
- 拆分任务时 → 你 MUST 仅在评审者能有意义地拒绝一个任务、同时批准相邻任务的边界处拆分。
- 对每个任务 → 任务 MUST 以能独立测试的交付物结束。
- 定义任务时 → 你 SHOULD 纵向切分任务（曳光弹）：每个任务端到端穿过各层，产出可观察的行为，而非一次构建一个水平层。
- 定义任务时 → 你 MUST 让每个任务能放进一个全新上下文窗口：一次实现者会话能同时容纳任务说明、涉及文件和测试。
- 工作是大范围机械重构（重命名或涉及多个文件的 API 迁移；此时不适用纵向切分）→ 读 `@wide-refactors.md` 并照做，按扩展—收缩顺序安排。
- 对每个任务 → 任务 MUST 用 `Blocked by:` 行声明依赖边（任务编号或 `none`）。
- 排列任务顺序时 → 计划执行顺序 MUST 遵循已声明的依赖边。
- 任务声明为独立 → 任务 MUST 列出 `Blocked by: none`。

## 细小步骤的粒度

- 对每个步骤 → 步骤 MUST 是一个具体动作——一个测试、一个最小实现、一条命令，或一次提交。
- 步骤捆绑了多个动作 → 步骤 MUST 拆开。
- 确定步骤大小时 → 步骤 SHOULD 小到几分钟内能完成。
- 对每个任务 → 步骤 MUST 遵循 TDD 周期，每项各占一个步骤：
  - “编写失败的测试”
  - “运行测试，确认失败”
  - “实现让测试通过的最少代码”
  - “运行测试，确认通过”
  - “提交”

## 计划文档头部

对每份计划 → 计划 MUST 以下列头部开始：

```markdown
# [功能名称] 实现计划

> **给实现者：** 逐个任务实现本计划。每个任务完成并验证后再开始下一个。步骤使用复选框（`- [ ]`）语法跟踪；仅在步骤完成后勾选——命令步骤在命令运行且产出预期输出后勾选；代码或测试步骤在按要求写入内容后勾选。

**目标：** [用一句话描述要构建什么]

**架构：** [用 2-3 句话说明做法]

**技术栈：** [关键技术/库]

## 全局约束

[规格中适用于整个项目的要求——最低版本、依赖限制、命名和文案规则、平台要求——每项一行，精确值从规格逐字复制。每个任务的要求都默认包含本节。]

---
```

- 填写全局约束时 → 值 MUST 从规格逐字复制。
- 复制最低版本、名称或文案字符串时 → 你 MUST NOT 改写。

## 任务结构

对每个任务 → 任务 MUST 遵循以下结构：

````markdown
### 任务 N：[组件名称]

**Blocked by:** [本任务依赖的任务编号，或 `none`]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**Interfaces：**
- Consumes：[本任务使用前序任务的哪些内容——精确签名]
- Produces：[后续任务依赖哪些内容——精确函数名、参数类型和返回类型]

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试，验证失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，提示 "function not defined"

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试，验证通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature" -- tests/path/test.py src/path/file.py
```
````

- 指定文件路径时 → 路径 MUST 精确。
- 对每个任务 → `Interfaces` 块 MUST 列出精确签名。
- 选择测试运行器、语言和命令时 → 你 MUST 使用宿主项目实际使用的测试运行器、语言和命令。
- 提交形式——宿主约定。
- 宿主声明了 `vcs` 约定——位于 `Omnipowers` 章节的一行、贡献指南或提交标准中 → 每个任务的提交步骤 MUST 遵循约定，包括如何暂存文件和编写提交信息。

## 危险信号

- 对每个步骤 → 步骤 MUST 包含工程师所需的实际内容。
- 编写计划时 → 你 MUST NOT 写出表中的任何模式：

| 计划中的危险信号 | 修正方式 |
|---|---|
| “TBD” / “TODO” / “稍后实现” / “补充细节” | 现在解决；写出具体内容 |
| “添加适当的错误处理” / “添加校验” / “处理边界情况” | 展示精确的处理代码 |
| “为上述内容编写测试”，却没有实际测试代码 | 写出实际测试代码 |
| “类似任务 N” | 重复完整代码 |
| 步骤只说做什么，没说怎么做 | 加入代码块或精确命令 |
| 引用了类型、函数或方法，但没有任务定义它 | 在前序任务的 `Produces` 和正文中定义 |
| 任务间名称不同（`clearLayers` 与 `clearFullLayers`） | 让所有位置的名称一致 |
| 文件路径含糊 | 写出精确路径 |
| 任务太大，无法独立评审 | 调整到合适大小 |
| 一份计划含多个独立子系统 | 拆成每个子系统一份计划 |

## 自我评审

完整计划写完后 → 你 MUST 换个视角，对照规格评审，亲自检查以下清单：

1. **规格覆盖：** 对规格的每一节或每条要求 → 你 MUST 指出实现它的任务，且 MUST 列出所有缺口并补充缺失任务来闭合缺口。
2. **占位符扫描：** 自我评审时 → 你 MUST 在计划中搜索危险信号表的每种模式，逐一修正。
3. **类型一致性：** 自我评审时 → 后续任务使用的类型、方法签名和属性名 MUST 与前序任务的定义一致。
   发现不一致 → 不一致处 MUST 统一。

自我评审发现问题 → 你 MUST 直接在原文修正。
修正新增或重命名了任务、步骤、类型或符号 → 你 MUST 对变更内容重新执行检查 2 和 3。

## 执行交接

- 保存计划后 → 你 MUST 报告保存路径并向用户呈现执行选项，然后等待用户选择。
- 用户尚未选择执行选项 → 你 MUST NOT 开始执行计划。

**报告模板：** “计划已完成并保存到 `<解析后的路径>`。有两种执行选项：”

1. **逐任务隔离执行**——一次实现一个任务，每个任务使用全新上下文，任务间设置评审闸门。
2. **会话内批量执行**——在本会话中实现任务，在检查点暂停以供评审。

- 用户选择逐任务隔离执行，且宿主环境提供为每个任务派发隔离执行者的机制（subagent 或并行 agent 能力） → 你 MAY 使用：每个任务一个执行者，下一个任务开始前评审当前任务的 diff。
- 用户选择逐任务隔离执行，但宿主没有这种机制 → 你 MUST 降级到可移植的会话内等价流程：完整实现每个任务、运行测试、评审 diff 并提交后，再阅读下一个任务。
- 用户选择逐任务隔离执行，但宿主没有这种机制 → 你 MUST NOT 在实现当前任务时提前阅读后续任务。

用户选择任一执行选项后 → 实现者 MUST 严格按顺序逐个执行任务，MUST 完成每个任务的 TDD 周期，且 MUST 在继续前提交。
