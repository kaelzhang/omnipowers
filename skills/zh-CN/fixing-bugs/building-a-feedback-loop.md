# 构建反馈回路

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

反馈回路 — 一条能因当前 bug 变红、修复后变绿、运行时不用人值守的命令。

## 路径列表 — 从成本最低的开始尝试

形成假设前，你 MUST 建立可运行的反馈回路。反馈回路 MUST 产生所选路径对应的红信号，而非仅仅“运行过”。

1. 失败测试 — 在能触达 bug 的接缝处编写测试，通过宿主项目的测试运行器执行；红信号：针对症状的断言失败。
2. HTTP 脚本 — 用 `curl`/`httpie` 脚本访问本地运行的服务；红信号：状态码或响应体错误。
3. CLI 调用 + 快照 diff — 用 fixture 输入运行程序，把 stdout/stderr/exit code 与已知正确的快照比较；红信号：diff 非空。
4. 无头浏览器脚本 — 用 UI 自动化对 DOM 状态、控制台错误或网络流量做断言；红信号：断言失败。
5. 追踪 / 日志回放 — 隔离运行失败的代码路径，回放捕获的请求、载荷或事件日志；红信号：输出错误。
6. 临时 harness 脚本 — 启动足以用单次调用触发 bug 的系统部分；红信号：结果错误。
7. 性质测试 / fuzz 回路 — 症状为“有时输出错误”时，用生成的输入检查 bug 违反的性质；红信号：反例。
8. 二分 harness — 用脚本检查已知正确和已知错误的提交、数据集或版本之间的状态；退出码 0：正确；红信号：退出码 1。
9. 差分回路 — 把相同输入传给两个实现或配置，再比较输出；红信号：diff 非空。
10. 人参与的脚本 — 针对物理设备、agent 无法处理的凭据，或只有用户能访问的环境，引导人逐项完成精确清单并记录观察结果的脚本。

临时反馈回路产物 — 回放捕获数据、harness 脚本和人参与的脚本；角色：**scratch**。

临时反馈回路产物 MUST 留在宿主项目内 — 放在 `Omnipowers` 声明为 `scratch` 指定的位置，否则放在 `.omnipowers/debug/` 下 — 并且这些产物 MUST 在调试结束时删除。

所有路径均已尝试 → 你 MUST 停下并明确告诉用户：列出尝试过的办法，请求能复现故障的环境、捕获的产物（日志转储、追踪、录屏），或添加临时探针的许可。没有反馈回路时，你 MUST NOT 进入假设阶段。

## 路径 10 — 人参与的脚本

上面的自动化路径中仍有未尝试的路径 → 你 MUST NOT 退回人参与的路径。

采用人参与的路径时 → 脚本 MUST 捕获观察结果，而非只发出指令。

## 模板

```bash
#!/usr/bin/env bash
# 人参与的复现清单。
# agent 编辑步骤；用户运行脚本并按提示操作。
# 捕获的答复按 KEY=VALUE 逐行输出，供 agent 解析。
set -euo pipefail

step()    { printf '\n>>> %s\n' "$1"; read -r -p "    [完成后按回车] " _; }
capture() { local v="$1"; printf '\n>>> %s\n' "$2"; read -r -p "    > " a; printf -v "$v" '%s' "$a"; }

# --- 编辑下方清单 -------------------------------------------
step    "启动应用，以普通用户身份登录。"
capture FAILED   "触发<精确操作>。故障是否出现？(y/n)"
capture EVIDENCE "粘贴完整错误消息或错误值（没有则填 'none'）："
# --- 清单结束 -------------------------------------------------------

printf '\n--- captured ---\n'
printf 'FAILED=%s\nEVIDENCE=%s\n' "$FAILED" "$EVIDENCE"
```

## 测试假设前收紧反馈回路

- 测试假设前 → 反馈回路 MUST 断言用户描述的精确症状 — 具体错误值、缺失的错误或时序 — 并且反馈回路 MUST NOT 满足于“没有崩溃”。
- 测试假设前，且 bug 本身并非非确定性问题 → 反馈回路 MUST 每次运行都给出相同结论：固定时钟、设定随机数生成器种子、隔离文件系统、对网络使用 stub 或冻结网络。
- 测试假设前 → 反馈回路 SHOULD 在数秒内完成：缓存准备工作、跳过无关初始化、把范围收窄到失败路径。

## 非确定性 bug — 提高复现率

故障间歇出现 → 你 MUST NOT 在复现率低到无法区分信号与运气时测试假设。

间歇失败来自测试等待任意时长的延迟 → 读 `@condition-based-waiting.md` 并照做。

## 最小化 — 剩余的每个元素都影响复现

反馈回路稳定变红 → 你 MUST 在第 3 阶段前缩减复现：**每次移除一个元素**，逐一移除输入、数据、配置、步骤和代码，每次移除后都重新运行反馈回路。

最小复现 — 移除任何剩余元素都会使故障消失的复现。

复现未满足最小复现标准 → 你 MUST NOT 宣布最小化完成。
