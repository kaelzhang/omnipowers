# 调查根因

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

失败测试未能直接揭示根因 → 你 MUST 在任何修复前完成本调查流程。

## 收集证据

- 你 MUST 完整阅读错误信息：完整消息和堆栈、行号、文件路径、错误码。你 MUST NOT 跳过警告。
- 你 MUST 检查可能引入故障的近期改动：diff、近期提交、新依赖、配置和环境差异。
- 故障跨越组件 → 提出修复前，你 MUST 在每个边界添加诊断日志 — 输入、输出、每层的配置和状态 — 运行一次，阅读证据，定位失败的层。
- 故障跨越组件 → 你 MUST NOT 猜测哪一层出错。
- 边界位于授权修改范围外 → 探针 MUST 仅用于观察：行为保持不变，每处编辑带有可搜索标签，不提交任何改动，工作结束前移除所有探针并验证移除。
- **仅观察的权限范围** — 只涵盖探针；这个区域的修复通过宿主自己的机制交给负责人。
- 错误出现在调用栈深处 → 你 MUST 反向追踪 — 错误值从何而来、谁传入了它 — 直到找到源头。

调用链很长，或无法靠阅读代码追踪 → 读 `@root-cause-tracing.md` 并照做。

## 与正常工作的代码比较

你 MUST 在同一代码库中找到相似且正常工作的代码，完整阅读你所遵循的参考资料或模式，列出正常和失败情况的每一处差异，并识别代码依赖的组件、配置和假设。

比较差异时 → 你 MUST NOT 以“这不可能有影响”为由忽略差异。

## 假设与测试

- 测试任何假设前 → 你 MUST 列出 3–5 个候选假设，并按可能性排序。
- 每个候选假设 MUST 陈述可证伪的预测 — “如果原因是 X，探针 P 会显示 Q”。
- bug 较为重大 → 你 SHOULD 把排序后的列表作为不阻塞工作的检查点告知用户，同时继续工作。
- 测试假设时 → 你 MUST 先测试排名第一的假设，每次只测一个假设，采用尽可能小的改动。
- 测试假设时 → 你 MUST NOT 同时改动多处。
- 每个探针 MUST 对应一个具体假设的预测。
- 探测时 → 你 MUST NOT “把所有东西都记日志再 grep”。
- 宿主授权使用调试器或 REPL → 你 SHOULD 优先使用它。
- 每个临时探针 MUST 带有一个唯一的标签前缀。
- 假设得到证实 → 你 MUST 回到修复循环。
- 假设未得到证实 → 你 MUST 按排序转到下一个假设，并且你 MUST NOT 在失败的修复上继续叠加修复。

## 3 次及以上修复失败时 — 质疑架构

三次及以上修复失败 → 你 MUST 停止尝试修复，与用户讨论架构问题：这个模式是否合理，还是我们一直在修补错误设计的症状？

讨论前 → 你 MUST NOT 尝试第 4 次修复。

## 没有代码根因时

完成调查后确认根因属于环境因素、依赖时序的因素或外部因素 → 你 MUST 记录调查内容，实现适当处理（重试、超时或明确报错），并添加日志供后续诊断。

得出没有代码根因的结论前 → 你 MUST 先确认本调查流程确实已完成。
