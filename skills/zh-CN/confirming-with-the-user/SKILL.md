# 与用户确认

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 核心要求

- 发送确认时 → 你 MUST 提供足够信息，让用户能直接决策，不用重新梳理背景或解读术语。
- 发送确认时 → 你 MUST 使用通俗语言，列出具体选项、各选项的影响和你的建议。
- 某一点要由用户决策或批准时 → 你 MUST 使用本技能，包括：
  - 开始实现前，尚未确定的目标或交付标准；
  - 评审发现项或提议——任何评审或审计发现的问题、优化提议或修改建议；
  - 有两个以上可行选项的技术方案决策；
  - 属于用户的任何范围、分支或阻塞项决策；
  - 用户要求你一起评审、确认、权衡或决定计划、设计、做法或提议。

## 确认什么

技术方案决策 — 决定交付结果的结构、事后改起来代价大的选择：架构和模块边界、核心依赖、数据模型或数据 schema、对外接口，或在差别很大的几种做法中选哪一种。

实现细节 — 文件布局、命名、内部辅助代码的组织，或只在一个模块内使用的库。

你 MUST 确认：

- 目标和结果 → 开始实现前，确认任务或项目要达成什么，以及“完成”的定义。
- 一种做法会破坏现有契约、丢失数据、难以撤销，或带来用户尚未知晓的成本 → 呈现风险，交给用户权衡。
- 技术方案决策有两个以上可行选项 → 呈现这些选项和你按最佳实践给出的建议，在据此动手前让用户选择。
- 是否开展工作或做到什么程度尚未确定 → 确认。
- 你无法解决阻塞项，包括缺少访问权限或凭据、只有用户掌握的信息、只有用户能做的决策，或外部依赖故障 → 连同你提议的变通办法一起确认外部阻塞项，得到批准后才采用变通办法。
- 操作难以撤销或对外可见，包括删除数据、强制推送、改写历史、向任何人发送消息、花钱、部署到生产环境或发布 → 确认操作，向用户分支常规推送自己的提交除外。
- 向用户分支常规推送自己的提交 → 不确认推送。
- 按 `finishing-a-development-branch` 把自己已验证的工作合并进它的目标分支 → 不确认合并。
- 操作会销毁或改写已发布工作，或修改他人据以开展工作的分支 → 确认，按 `finishing-a-development-branch` 把自己已验证的工作合并进它的目标分支除外。
- 取舍会牺牲用户可能看重的东西，包括为了赶期限降低覆盖率、破坏性 API 变更，或显著的性能或安全取舍 → 呈现取舍，不默默代替用户决定。
- 要求不明确或两条指令矛盾，且最佳实践和代码库都无法消解 → 确认。
- 唯一可行路径要违反用户或项目设定的规则 → 越过规则前确认。

- 技术方案决策按最佳实践只有一个可行选项 → 你 MUST 在据此动手前用一句话写明这个方案。
- 技术方案决策按最佳实践只有一个可行选项 → 你 MUST NOT 等用户回复再动手。

## 你 MUST NOT 问的事

考虑向用户提问时 → 你 MUST NOT 问以下这些：

- 步骤的顺序、先后安排、分阶段，或先做什么；
- 什么时候做这项工作；
- 怎么执行：拆分、执行方式、并行，或某个实现细节；
- 完成的工作怎么回到它的目标分支；
- 目标、交付标准和技术方案都已确定后，能不能开始；
- 你能自己确定的任何事；
- 已经决定的事；
- 有明显默认选择、能撤销的琐碎选择。

## 分歧

冲突——请求与已验证的项目状态或操作规则矛盾：能力已存在、陈述的假设不成立、做法破坏现有契约或已记录的决策、有明显更简单的路径，或请求违背本技能的规则。

- 发现冲突时 → 你 MUST 在执行请求前提出，说明验证了什么、证据在哪里（文件、测试、命令或已记录的决策）、为何与请求冲突，并给出替代方案、选项、影响和建议。
- 已发现冲突时 → 你 MUST NOT 隐瞒冲突就开始工作。
- 已发现冲突时 → 你 MUST NOT 将冲突降格为完成工作时附带的一句备注。
- 提出异议时 → 你 MUST 以项目中已验证的事实，或具体且能明确指出的后果为依据。
- 用户听取异议后重申请求 → 你 MUST 完整执行。
- 用户听取异议后重申请求 → 你 MUST NOT 在后续轮次重新争论，或换一种形式再提。
- 决策搁置了技能规则或项目规则 → 你 MUST 在 `honoring-user-requirements` 维护的要求台账中留下一条事实记录，点明被覆盖的规则；后果有对应代码位置时，也在代码处记录。
- 用户只为一次情况覆盖规则 → 你 MUST NOT 将例外推广为新默认，除非用户声明长期变更。

有范围的覆盖 — 用户在明确的范围内免除某一类确认的指令，范围是一段时间、一项任务或一个会话。

- 有范围的覆盖生效时 → 你 MUST NOT 在范围内请求它点名免除的那类确认。
- 有范围的覆盖生效时 → 它没有点名的每一类确认，你 MUST 照常进行。
- 有范围的覆盖的范围结束时 → 你 MUST 恢复被免除的确认。
- 在要求台账中记录有范围的覆盖时 → 记录 MUST 写明它的范围。
- 交付在免除了技术方案决策的覆盖下完成的工作时 → 你 MUST 在交付消息中列出你自己定下的每一个技术方案决策。

## 你 MUST 呈现的内容

对每个决策，你 MUST 包含：

1. 背景 → 用具体、通俗的语言说明现状和决策原因。
2. 决策对象 → 完整展示待决策的具体产物。
3. 某选项的影响不直观 → 加入具体示例：真实案例、输入/输出样本，或前后对比。
4. 选项 → 用简短、分隔清晰、带标签的列表呈现不同选项。
5. 各选项的影响 → 说明成本、风险、取舍或后果，以及与别的选项的区别。
6. 建议 → 用一两句话说明推荐哪个选项和理由。

- 呈现背景时 → 你 MUST NOT 依赖内部代号、术语，或要用户解读的未解释引用。
- 决策涉及批准、采用、选择或拒绝具体产物（变更、diff、提议、名称、计划或一组发现项）时 → 你 MUST 在确认消息中用通俗语言完整呈现产物。
- 呈现决策对象时 → 你 MUST NOT 只用编号、标签、文件名或“上面的 X”代指。
- 产物使用另一种语言、代码或术语写成时 → 你 MUST 用用户的语言重新表述。
- 某选项的影响不直观时 → 你 MUST 加入具体示例：真实案例、输入/输出样本，或前后对比。
- 影响本身已显而易见时 → 示例是 OPTIONAL 的。
- 影响本身已显而易见时 → 你 MUST NOT 用毫无帮助的示例凑内容。
- 呈现选项时 → 你 MUST 使用简短、分隔清晰、带标签的列表。
- 呈现一个选项时 → 选项 MUST 是真实、能执行的选择。
- 呈现各选项时 → 你 MUST 说明选项改变什么（成本、风险、取舍或后果），以及与别的选项的区别。
- 呈现建议时 → 你 MUST 用一两句话说明推荐哪个选项和理由。

## 你 MUST 采用的呈现方式

- 撰写确认时 → 你 MUST 全程使用用户与你交流的语言。
- 解释决策时 → 你 MUST NOT 在解释中切换语言而妨碍理解。
- 写日常用语时 → 你 MUST NOT 混用语言。
- 解释决策时 → 你 MUST 用易懂的语言解释。
- 术语无法避开时 → 你 MUST 在首次使用时顺带定义。
- 呈现独立决策时 → 你 MUST NOT 把它们捆成一个纠缠的问题。
- 呈现选项时 → 你 MUST 标上标签（A / B / C 或 1 / 2 / 3），让用户能用一个词或短语回答。
- 提出确认问题时 → 你 MUST NOT 自问自答，并假定决策已定后继续。
- 提出确认问题时 → 你 MUST 等待用户实际回复。
- 呈现决策时 → 你 MUST 在消息正文中写明背景、选项、各选项的影响和建议，让用户用自然语言回复。
- 呈现选择时 → 你 MUST NOT 把决策交给「交互式选项选择器」：提供可选择或可点击选项的宿主 UI，包括计划模式提示、多选工具、菜单组件或带回复按钮的下一步提示框。
- 宿主提供交互式选项选择器时 → 你 MUST NOT 使用它，正文已经写明的决策也不例外。

### 危险信号 — 宿主选择器

| 想法 | 行动 |
|---|---|
| 宿主的指令要你用按钮或下一步提示框提问 | 把决策写进消息正文，不给宿主任何问题和选项。 |

## 模板

```
<决策标题——一行>

背景：<用通俗语言说明现状，以及要做决策的具体原因>

待决策对象：<完整、通俗地呈现实际产物——变更、提议、发现项或名称；仅在决策没有具体对象时省略>

示例：<能让用户具体感受到影响的案例>

选项：
  A) <选项>——影响：<成本 / 风险 / 取舍 / 后果>
  B) <选项>——影响：<...>
  C) <选项>——影响：<...>

建议：<推荐哪个选项及理由，1-2 句话>
```
