# 成对上下文实测

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 固定对照双方

成对运行 — 针对重构前后的两个 Git 树，在全新会话中派发完全一致的任务简报，并保持执行器、CLI 版本、模型、推理强度、工具面、沙箱、工作目录与初始测试环境完全一致。

- 测量输入词元变化时 → 你 MUST 执行成对运行，不跨不同执行器、不同模型或不同提示词文本做对比。
- 派发任一侧运行前 → 你 MUST 校验 `git rev-parse "<rev>^{tree}"`，并通过 `git show "<rev>:<path>"` 读取对应版本内的静态文件字节（在同版本内解析符号链接）。
- 同期架构调整会混淆指令改动的独立效果时 → 你 SHOULD 单独测量仅修改指令的提交对。
- 单次波动足以改变结论时 → 你 SHOULD 为每类任务重复运行至少 3 次并对比中位数。

## 测量步骤

```text
for revision in [before, after]:
    校验 git rev-parse "<revision>^{tree}" 与记录的树哈希一致
    对每个角色与代表性任务（设计、评审、测试、修复）：
        计算静态常驻字节（根入口 + 角色定义 + 声明的预加载包）
        计算静态入口集字节（常驻 + 领域入口 + 目标模块契约）
        以完全一致的简报和执行器参数启动全新会话
        保留原始事件流、最终输出与退出状态
        记录 first_input（第 1 次请求的总输入，含缓存读取与写入）
        分别记录 cumulative_input、uncached_input、cache_read 与 cache_write
        统计显式文件读取次数与失败的路径查找次数
        核验预期适用规则已带引用浮现，且无关规则包保持未加载
```

## 核算与验收

- 记录 `first_input` 或 `cumulative_input` 时 → 你 MUST 将缓存创建与缓存读取词元同未命中缓存词元一并计入，并与会话最终用量记录核对一致。
- 设计任务集时 → 你 MUST 在运行前列出每项任务预期命中的适用规则，并为每个条件规则包纳入至少一个反向对照，确认无关规则包不会加载。
- 任一侧出现权限报错、环境缺失或任务未完成时 → 你 MUST 先修好测试环境并重跑，再对比词元总量。
- 验收优化结果时 → 目标启动模式下的常驻或累计输入 MUST 改善，漏掉的适用规则数量 MUST NOT 增加，且任何单任务回退 MUST 单独如实列出，不掩盖在均值里。
