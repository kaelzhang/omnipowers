# 编写文档

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 范围

长期文档 — `README.md` 文件、架构与工程文档、服务 / 产品 / 运维文档、贡献者与 agent 入口，以及未来读者为正确工作而要加载的 Markdown。

临时文字 — 临时计划、任务笔记、聊天、提交消息、PR 描述和评审评论；除下方清晰表达及权威链接建议外，不在本技能范围内。

- 编写临时文字时 → 文字 SHOULD 清晰。
- 临时文字依赖权威文档 → 文字 SHOULD 链接到权威文档。

### 与其他技能的边界

- `writing-skills` — 负责技能编写（`SKILL.md` 及辅助文件）的技能。
- `writing-handoffs` — 负责压缩本次会话以交给下一个 agent 的技能。
- `writing-plans` — 负责编写实现计划的技能。
- `researching` — 负责研究发现项文件的内容和声明引用的技能；只有文件加入持久文档组时，才进入本技能范围。
- `domain-modeling` — 负责领域术语含义和需留档决策的技能；本技能负责术语表和记录的访问路径及写法。

## 铁律

```
每份文档都从所在文档组的入口到达，不靠逐个扫描
```

- 编写文档时 → 你 MUST NOT 让读者打开目录中的每个 Markdown 文件来判断哪份适用。

## 入口契约

- 对于每组文档 → 文档组 MUST 恰好有**一个**入口。
- 对于每组文档 → 入口 MUST 回答全部四个问题：
  1. **文档组负责什么** — 用一行说明它约束的工作。
  2. **如何选择文件** — 读者按任务信号选择，还是整组都要读；明确写出。
  3. **具体读哪些文件** — 逐一写明准确路径。
  4. **默认跳过什么** — 对于按任务选择的文档组，任务范围未扩展到相邻文件时不加载这些文件。
- 使用任一入口模板时 → 契约内容 MUST 完整保留。

### 形式 A — 按任务信号解析

```markdown
# <领域>

<一行：这组文档约束的工作。>

## 加载映射

| 任务信号 | 阅读 | 任务范围未扩展时跳过 |
| --- | --- | --- |
| <与读者实际任务匹配的条件> | `<exact-file.md>` | `<不加载的相邻文件>` |
```

### 形式 B — 全部阅读

```markdown
# <领域>

<一行：这组文档约束的工作。>

## 阅读要求

开始前阅读这组文档中的每份文档：

- `<exact-file.md>` — <约束的工作>
```

- 对于一组文档 → 你 MUST NOT 留下两个仍在使用的入口。

## 解析表

- 选择路由机制时 → 你 MUST NOT 将生成的索引、清单、机器可读数据文件或脚本用作路由机制。
- 用于路由以外的用途时 → 这些产物 MAY 存在。
- 编写入口时 → 入口 MUST NOT 将读者引向这些产物。
- 编写信号时 → 信号 MUST 是描述读者**即将做什么**的自然语言条件，不复述文档标题。
- 编写解析路径时 → 路径 MUST 准确，并 MUST 能从入口自身目录解析。
- 对于组内每份文档 → 文档 MUST 至少出现在表格某一行的“阅读”或“任务范围未扩展时跳过”栏中。
- 编写信号时 → 信号 SHOULD 只指向少量要加载的文件。
- 信号引入组内大部分文档 → 信号 MUST 拆分为更窄的信号。
- 编写入口时 → 入口 MUST 说明没有信号匹配时怎么做：阅读最小且可能适用的单份文档，或询问。

## 路径解析

- 编写相对路径时 → 路径 MUST 从承载路径的文档所在目录解析。
- 路径采用另一基准（仓库根目录、工作区根目录或读者 shell 的工作目录） → 基准 MUST 紧邻路径写明。
- 描述约定时 → 占位模式 MAY 用于描述约定。
- 引用实际文件时 → 引用 MUST 是从当前文档出发有效的真实路径。

## 信息密度

- 编写文档时 → 你 SHOULD 使用保留规范含义的最短文字，省去不影响规则应用的理由，以及不能消除歧义的示例。
- 对于每条规则 → 规则 MUST 恰好有一个来源，但受下方独立文档限制约束。

## 不重复规则的边界

- 文档设计为**单独**加载 → 文档 MUST 包含正确应用所需的全部内容，即使相邻文档有相同内容。
- 删除任何重复内容前 → 你 MUST 判断两份文档是否会一起加载。
- 任一文档会单独加载 → 入口 MUST 指明哪份副本具有权威性。

## 同次变更的义务

- 添加、删除、拆分、重命名文档或调整文档范围时 → 变更 MUST **在同次变更中**更新文档组入口。
- 修改文档时 → 变更 MUST 扫描同组内相邻文档，检查本次变更**引入或暴露**的重复，并在同次变更中解决，但受上方独立文档限制约束。
- 入口超出你在项目中的写入权限 → 你 MAY 仅在此条件下交付未更新入口的文档变更。
- 使用此例外时，在认定变更完成前 → 你 MUST：
  1. 说明入口准确路径，以及当前要添加或修改的具体行。
  2. 取得用户对入口更新方式的明确指示。
  3. 在回复中保留请求，不只留在推理中。

## 危险信号 — 要先修复

- 即将修改的文档组没有入口、有多个入口，或入口与磁盘内容不符 → 读 `@repairing-a-doc-set.md` 并照做，再修改文档。

## 职责范围外的发现项

- 发现的重复、失效路径或结构缺陷不在用户要求修改的范围内 → 你 MUST 在回复中向用户指出准确路径和具体重叠，写明文件及问题。
- 发现的重复、失效路径或结构缺陷不在用户要求修改的范围内 → 你 MUST NOT 默默重组。

## 文档位置

- 文档描述现有目录、包或模块，且宿主项目未刻意集中管理文档 → 文档 SHOULD 放在对应目录。
- `design-docs` — 没有明确归属的新持久文档组的产物角色；位置按 `using-omnipowers` 解析，回退路径为 `docs/`。
- 宿主已使用入口文件名 → 你 MUST NOT 在旁边引入第二种入口文件名。
- 文档是宿主自己的**标准**（评审检查清单、编码规则或工作评判标准） → 你 MUST NOT 自行重组。
