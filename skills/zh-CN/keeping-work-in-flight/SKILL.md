# 保持工作推进

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 铁律

```
先派发再阅读 — 先清点再收尾 — 只有受追踪的调用能唤醒你
```

## 派发块

agent、subagent 或后台任务返回，或轮次即将结束时 → 你 MUST 在阅读任何报告和撰写回复的任何部分前，按顺序运行以下四步：

1. 统计仍在运行和排队的工作。
2. 列出每个空闲且有排队工作的职责范围。
3. 为每个空闲范围派发一个受追踪的调用。
4. 阅读报告，作出判断，再撰写回复。

队列为空时 → 你 MUST 在宣告本轮完成前检查：接下来要做的工作是否能拆成同时运行的部分。

独立性测试 — `@fanning-out.md`，适用于检查接下来的工作是否能拆成并发部分。

## 以受追踪的形式启动

- 即将启动的工作会在启动它的调用结束后继续运行时 → 你 MUST 使用宿主列为活跃工作、且完成后会重新调用你的形式启动。
- 受追踪的形式存在时 → 你 MUST NOT 将工作放入后台后轮询，且你 MUST NOT 安排定时唤醒来检查工作。
- 无法指出宿主在哪里列出这项运行中的工作时 → 你 MUST NOT 将“它在某处运行”视为已派发。
- 派发受追踪时 → 你 MUST NOT 通过 PID 等待、轮询循环、睡眠后检查或任何其他方式等待它。

## 每个范围一个受追踪的调用

- 派发 N 项工作时 → 你 MUST 发出 N 个独立的受追踪调用。
- shell 循环在一个调用内将 N 个进程放入后台时 → 你 MUST NOT 使用它。
- 需要任务结果时 → 任务本身 MUST 就是受追踪的调用。
- 只需要进程保持存活、没有结果要等待时 → 进程 MUST 在启动它的 shell 结束后继续存活。
- 某种形式在几秒内报告完成，而进程仍在运行时 → 你 MUST NOT 使用它。

- 选择后台形式、关闭委派运行的 stdin、轮询或结束委派运行时 → 读 `@dispatch-mechanics.md` 并照做。
- 你是即将启动 `codex exec` 运行的 Claude Code agent 时 → 读 `@codex-from-claude-code.md` 并照做。

## 派发前

派发块找到空闲且有排队工作的范围时 → 读 `@fanning-out.md` 并照做。

- 派发块找到空闲且有排队工作的范围时 → 每个候选任务 MUST 通过独立性前置条件，且每次派发 MUST 携带文件指定的内容，包括宿主没有 subagent 的情况。

## continuation — 跨轮次工作

continuation 承接用户已经批准的目标时 → 你 MUST NOT 用它越过用户掌握的决策。

## 心跳

- 你 MAY 安装定期报告，仅说明：运行中的任务数、空闲范围、最近提交和未推送提交数。
- 已安装定期报告时 → 报告 MUST NOT 编辑、提交、派发或改变任何状态。
- 心跳事后发现空转时 → 你 MUST NOT 将它视为派发块的替代品。

## 危险信号 — 出现这些想法就停下

| 想法 | 改做什么 |
| --- | --- |
| “先读这份报告，再看还能启动什么。” | 先运行派发块。 |
| “循环比六次独立调用快。” | 发出六个受追踪的调用。 |
| “把构建放到后台，稍后再检查。” | 以受追踪的形式启动。 |
| “安排一次定时唤醒，看看是否完成。” | 以受追踪的形式重新启动。 |
| “只是一条长命令，不是并行工作，这条不适用。” | 每次派发都选择受追踪的形式。 |
| “已经受追踪地启动了，现在等 PID 结束。” | 启动后继续推进工作。 |
| “subagent 受追踪，我自己的后台脚本不一样。” | 自己的脚本也以受追踪的形式启动。 |
| “逐项做完更快。” | 先拆分，再派发。 |
| “没有工作在运行，不过反正快做完了。” | 先派发，再收尾。 |
| “等这个 agent 返回再说。” | 派发每个空闲范围，再读返回内容。 |
| “这两个任务几乎不重叠。” | 不并行执行它们。 |
| “那个目录归别人负责，但改动很小。” | 转交给负责人。 |
| “在回复里记下下一步。” | 写入宿主的 work-state。 |
| “停滞了，心跳会发现。” | 运行派发块。 |
