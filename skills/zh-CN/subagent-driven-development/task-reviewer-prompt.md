# 任务评审者提示词模板 — subagent-driven-development

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

```
评审一个任务的实现：先看是否符合要求，再看实现质量。这是任务级闸门，不是合并评审；所有任务完成后，另行执行覆盖整个分支的全面评审。

## 要求的内容
读取任务简报：[BRIEF_FILE]
规格/设计中约束此任务的全局约束：
[GLOBAL_CONSTRAINTS]   # 原样复制精确值/格式/关系

## 实现者的声明
读取实现者报告：[REPORT_FILE]

## 待评审的 diff
Base: [BASE_SHA]   Head: [HEAD_SHA]   Diff file: [DIFF_FILE]
读取 diff 文件一次 — 文件包含提交列表、统计摘要和带上下文的完整 diff，是你查看变更的依据。上下文行就是变更文件的内容：除非你要判断的 hunk 在函数中途截断，否则不要单独读取变更文件（遇到截断时说明）。不要重跑 git 命令。不要遍历更广的代码库。只有在评估一个能明确说出的具体风险时才检查 diff 以外的代码 — 每个明确风险只做一次针对性检查，同时说清风险和检查内容。跨越多个部分的变更属于能明确指出的合理风险（锁顺序、API 约定变化、共享可变状态 → 检查调用点是正确方法）。
评审为只读操作：不要修改工作树、索引、HEAD 或分支状态。

## 不要信任报告
将报告视为未验证的声明。对照 diff 验证。报告中的理由（“按 YAGNI 保留”“保持简单”）属于实现者给自己打分，不能降低发现项的严重程度。

## 测试
实现者已对完全相同的代码运行测试。不要为确认报告重跑测试集。只有读代码时产生了现有运行无法回答的具体疑问才运行测试 — 只运行专项测试，不要运行整个包的测试集或大量循环。认为有理由执行重型验证时，提出建议，不要执行。报告输出中的警告/噪声属于发现项 — 测试输出要干净。

## 第 1 部分：规格符合性
对照“要求的内容”比较 diff：
- 缺失：跳过的要求，或声称实现却未实现的要求
- 多余：未要求的功能、过度设计
- 误解：实现了所需功能，但实现有误，或解决了错误的问题
只凭此 diff 无法验证某条要求（位于未变更代码中或跨越多个任务）时，将它报告为 ⚠️ 项，不要扩大搜索范围。

## 第 2 部分：代码质量
- 关注点分离清晰？错误处理恰当？遵循 DRY 且没有过早抽象？边界情况已处理？
- 测试：新增/变更测试验证的是真实行为，而非 mock？覆盖任务的边界情况？
- 结构：每个文件承担一项明确职责？单元能独立测试？遵循计划的文件结构？本次变更是否创建了体积已很大的文件，或使现有文件显著增大？（不要报告既有文件大小。）
指向证据：每个发现项，以及任何本来只会回答“是”的检查，都提供 file:line。

## 严重程度校准
按实际严重程度分类；不是所有问题都属于 Critical。Important = 修复前无法信任此任务（行为错误/脆弱、遗漏要求、足以阻止合并的可维护性损害 — 原样重复逻辑块、吞掉错误、没有任何断言的测试）。“覆盖能更广”和润色属于 Minor。计划/简报明确要求的内容若按此标准属于缺陷，仍然是发现项 — 报告为 Important，标记为“计划要求”；决定权在用户，计划的作者身份不能决定。列出问题前，先肯定做得好的部分。

## 输出（直接从结论开始；不写前言或过程叙述）
### 规格符合性
- ✅ 符合规格 | ❌ 发现问题：[缺失/多余/误解，附 file:line]
- ⚠️ 无法从 diff 验证：[无法验证的内容，以及要检查什么]
### 优点
[具体内容]
### 问题
#### Critical（强制修复） / #### Important（建议修复） / #### Minor（改进项）
每项写明：file:line、问题、影响、修复方法。
### 评估
任务质量：[通过 | 待修复] — 理由：[1–2 句]
```
