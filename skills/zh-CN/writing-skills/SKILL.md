# 编写技能

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 概览

- 开发技能时 → 你 MUST 遵循 RED → GREEN → REFACTOR：观察 agent 在没有技能时失败，编写只针对这些失败的指导，并堵住 agent 在压力下找到的每个漏洞。
- 产出技能时 → 技能 MUST 满足下列编写不变量。
- 编写规范性语句时 → 语句 MUST 用 BCP 14 关键词表达力度。
- 产出技能时 → 技能 MUST 包含单行 BCP 14 解释注释。
- 脆弱操作 — 场景明确、只有一个正确答案，且存在能指明的失败模式；你已观察到这种失败模式，或能具体论证它会在压力下出现。
- MANDATORY 分类 — MUST / MUST NOT，仅用于脆弱操作。
- 规则约束脆弱操作时 → 规则 MUST NOT 弱化为“考虑”或“试着”。
- 判断空间分类 — SHOULD / MAY，并说明判断随哪些情况变化。
- 定义 MANDATORY 规则时 → 规则 MAY 最多定义一个形如 `MAY <skip> ONLY when <condition>` 的例外出口，并以 MUST 检查清单、用户明确许可和持久记录为闸门。
- 产出技能时 → 技能 MUST 自包含，不引用宿主项目外的内容，且只通过同目录引用包含辅助文件。
- 产出技能时 → 技能 MUST 在任何宿主项目中以同样方式运行。
- 运行时 → 技能 MUST NOT 依赖编写、测试或优化工具。
- 技能需要状态时 → 技能 MUST 将状态保存在宿主项目内。
- 产出产物时 → 产物 MUST 归入 `design-docs`、`work-state`、`records`、`scratch` 或 `standards`，并写明回退路径；其余的位置解析交给 `using-omnipowers`。
- 产出技能时 → 技能 MUST 遵循宿主的提交惯例、隔离单位和 write-authority 模型。
- 技能违反这些不变量时 → 你 MUST NOT 用本技能为交付它辩护。

## 适用范围

创建技能、编辑技能或在部署前验证技能时 → 你 MUST 应用本技能。

出现以下任一想法时 → 你 MUST NOT 将任务视为本技能或基线要求的例外：
- “只是加一点内容。”
- “只是更新文档。”
- “只是加一节。”
- “只是一条显然的规则。”

### 何时创建技能

- 技术能在本任务外复用，且并非直觉就能掌握时 → 你 SHOULD 创建技能，综合权衡复用性、非显然性和适用范围，不让任何一项单独决定结果。
- 一次性解决方案没有复用价值时 → 你 MUST NOT 创建技能。
- 内容属于项目特定惯例时 → 你 MUST NOT 创建技能。
- 约束能由正则表达式、linter 或验证工具执行时 → 你 MUST NOT 创建技能；改用自动化，将技能留给判断问题。

### 调用方式

- 编写防止 agent 走捷径、保护用户的护栏技能时 → 技能 MUST 由模型调用。
- 编写会让日常任务承受过多流程的重型编排技能，或带有对外副作用的技能时 → 技能 SHOULD 仅在用户明确请求时启用：将 description 限定为用户的字面请求（“仅在用户明确要求……时使用”），并在宿主支持时使用仅手动调用的 frontmatter。

## 铁律

```
没有先失败的测试，就不写技能
```

- 编写或编辑技能内容前 → 除纯参考技能外，你 MUST NOT 在缺少基线的情况下继续；基线要展示技能旨在防止的失败。
- 尚未建立基线就先写了技能时 → 你 MUST 删除技能并重新开始。
- 尚未建立基线就先写了技能时 → 你 MUST NOT 将未经验证的草稿保留为“参考”。
- 尚未建立基线就先写了技能时 → 你 MUST NOT 一边跑基线一边“调整”草稿。
- 纯参考技能 — 只检索事实、没有可违反规则的技能。
- 技能包含 agent 有动机绕过的规则时 → 基线是 REQUIRED 的。

## 技能的 RED → GREEN → REFACTOR

### RED — 观察没有技能时的失败

- 运行 RED 时 → 你 MUST 让上下文全新的 agent 在没有技能的情况下执行真实场景。
- 运行 RED 时 → 你 MUST 观察 agent 自然采取的行为。
- 运行 RED 时 → 你 MUST NOT 跳过这一步。
- 构建基线场景时 → 你 MUST 按“编写压力场景”设置能诱发失败的条件。
- 学术式提示词 — 询问最佳实践怎么说，而不诱发失败的提示词；不算合格的基线场景。
- 运行 RED 时 → 你 MUST 运行无技能对照。
- 对照没有出现失败时 → 你 MUST 停止，不编写指导。
- 运行 RED 时 → 你 MUST 逐字记录 agent 的选择和自我开脱。
- 运行 RED 时 → 你 SHOULD 运行至少 3 个上下文全新的样本。
- 宿主环境提供 subagent 或并行 agent 时 → 你 MAY 将每个场景派发给一个全新的 subagent。
- 宿主没有 subagent 时 → 你 MUST 为每个场景开启上下文全新的会话，并手动运行。
- subagent 不可用时 → 你 MUST NOT 跳过基线。

### GREEN — 编写最小技能

- 编写 GREEN 指导时 → 你 MUST 只处理 RED 中捕获的具体自我开脱。
- 编写 GREEN 指导时 → 你 MUST NOT 为从未观察到的假设性失败添加对策。
- 写完技能后 → 你 MUST 在技能生效的情况下重跑相同场景。
- 在技能生效的情况下重跑这些场景时 → agent MUST 遵守规则。
- agent 仍然失败时 → 你 MUST 修改并重新测试技能。
- 技能“读起来没问题”时 → 你 MUST NOT 据此宣告成功。

### REFACTOR — 堵住每个漏洞

- agent 遵守原始场景中的规则，却在增加压力后找到新的自我开脱时 → 你 MUST 明确堵住漏洞并重新测试。
- 出现新的自我开脱时 → 你 MUST 重复这个循环，直到不再出现。

对每个新的自我开脱 → 你 MUST：
1. 在规则中加入明确的否定，点名封堵具体绕法。
2. 在技能的自我开脱表中添加一行。
3. 在技能的危险信号列表中添加一项。
4. 自我开脱是即将违规的症状时 → 将症状加入 `description` 触发条件。

## 按失败类型选择形式

- 编写指导前 → 你 MUST 对基线失败分类。
- 编写指导前 → 你 MUST 从下表选择形式，而非默认使用否定规则。
- 对表中的每种基线失败 → 你 MUST 使用指定形式。
- 对表中的每种基线失败 → 你 MUST NOT 使用排除的形式。

| 基线失败 | 指定形式 | 排除的形式 |
|---|---|---|
| 知道规则，却在压力下跳过 | 否定规则 + 自我开脱表 + 危险信号 | 温和指导（“优先”、“考虑”） |
| 遵守规则，但输出形式错误（臃肿、埋没、重复） | 正向步骤或契约：说明输出是什么，按顺序列出组成部分 | 否定清单（“不要重述”、“从不叙述”） |
| 在已经产出的内容中漏掉要求的元素 | 结构约束：在填写的模板中设置 REQUIRED 字段或槽位 | 模板附近的文字提醒 |
| 行为随条件变化 | 以可观察谓词为条件（“简报存在时，引用简报”） | 无条件规则 + 豁免条款 |
| 提前结束步骤、过早宣告完成 | 可检查且穷尽的完成标准，agent 能据此核对状态 | 文字提醒（“不要提前停下”、“做彻底”） |

- 定义例外时 → 例外 MUST 独立成条件规则，并以可观察谓词为条件。
- 输出的一部分要排除在规则外时 → 你 MUST 调整规则，将这部分移出范围，而非用文字豁免。

### 核心词

- 核心词 — 技能中简短、模型已通过预训练掌握的概念词。
- 同一技能内 → 近义词 MUST NOT 替代核心词。

### 删减现有技能

编辑现有技能时 → 你 MUST 同时删减：
- 删除当前模型在没有指导时也能正确遵循的行，用无指导对照验证，而非凭直觉。
- 每条规则在技能内只写一次，放在最能约束行为的位置；保留跨 SKILL 重复以维持自包含。
- 将指导沉积视为默认结果。

潜在沉积 — 为应对上一年模型的失败而编写的规则，这些规则 MAY 已不再值得占用上下文。

## 抵御自我开脱

- 编写执行纪律的技能时 → 技能 MUST 能抵御自我开脱。
- 纪律失败 — agent 知道规则，却跳过规则。

### 明确堵住每个漏洞

堵住纪律技能的漏洞时 → 你 MUST 点名封堵具体绕法，而非只陈述规则。

### 提前说明根本原则

编写纪律技能时 → 你 MUST 在开头附近加入一句等同于**“违反规则的字面要求，就是违反规则的精神。”**的话。

### 构建自我开脱表

编写纪律技能时 → RED 和 REFACTOR 中出现的每个借口 MUST 列入两列表格，点名借口并用具体表述驳回：

```markdown
| 借口 | 事实 |
|--------|---------|
```

编写纪律技能的自我开脱表行时 → 表行 MUST 反驳一个观察到的具体自我开脱，而非泛泛反驳（“别作弊”）。

### 创建危险信号列表

编写纪律技能抵御自我开脱的规则时 → 你 MUST 提供自查清单，用于识别正在自我开脱的想法。

### 说服力度

- 编写纪律技能时 → 你 MUST 采用权威和承诺框架：祈使句、强制明确选择、要求明确告知。
- 编写纪律技能时 → 你 MUST NOT 依赖好感或互惠（“如果你……就能帮到我”）。

## 编写压力场景

对每个场景 → 你 MUST 满足以下要求：
- 对每个场景 → 你 MUST 从时间、沉没成本、权威、经济、疲劳、社交和务实（“务实而非教条”）中组合至少 3 种压力。
- 对每个场景 → 你 MUST 给出明确选项（A/B/C），并要求 agent 选择并行动（“你怎么做？”）。
- 包含具体文件路径、时间和后果。
- 在每个场景中 → 场景中的 agent MUST NOT 有不作选择就转而回答“我会问用户”的退路。

## 先对措辞做微型测试

确定措辞前 → 你 SHOULD 用低成本微型测试验证措辞：
1. 每个变体运行一个上下文全新的样本，将完整技能作为真实的外围系统上下文，并提供能诱发失败的用户任务。
2. 包含无指导对照；对照没有失败时，停止。
3. 每个变体至少重复 5 次。
4. 将方差作为指标；重复运行产生不同解释时，先收紧形式，再增加文字。

对措辞做微型测试时 → 你 MUST 手动阅读每个标记的匹配项。

## GREEN 无法稳定时的元测试

agent 读过技能后仍然选错时 → 你 MUST 直接问它：

```markdown
你读过技能，却选错了。技能要怎么写，才能让正确选项毫无歧义？
```

## 纯参考技能

技能只检索事实、没有可违反的规则时 → 你 MUST 仍然验证实用性：
- 在检索测试中 → 上下文全新的 agent MUST 能为真实问题找到正确条目。
- 在应用测试中 → agent MUST 能正确应用找到的内容。
- 在缺口测试中 → 常见用例 MUST 得到覆盖。
- 技能包含 agent 有动机绕过的规则时 → 你 MUST NOT 声称“纯参考”来跳过基线。

## 反模式

交付技能时 → 你 MUST NOT 包含：
- 叙述单次事件的故事。
- 多语言稀释：用五种语言写五个平庸示例。
- 流程图内的代码。
- 没有语义的标签。

- 替换多语言稀释内容时 → 一个用最相关语言编写、完整出色且注释充分的示例是 REQUIRED 的。
- 包含代码时 → 代码 MUST 放在围栏代码块内。
- 包含参考材料时 → 参考材料 MUST 使用表格或列表。
- 包含线性步骤时 → 步骤 MUST 使用编号列表。
- 编写标签时 → 标签 MUST 承载含义。

## 停下 — 进入下一个技能前

- 编写或编辑技能后 → 你 MUST 完成全部验证，再开始另一个技能。
- 编写或编辑技能时 → 你 MUST NOT 批量创建，再统一测试。
- 当前技能验证完成前 → 你 MUST NOT 转向下一个技能。
- 出现“批量更高效”的想法时 → 你 MUST NOT 跳过测试。

## 技能开发检查清单

部署技能前 → 你 MUST 能勾选每个适用项：

**RED — 观察失败：**
- [ ] 构建了能诱发失败的场景（纪律技能组合至少 3 种压力）
- [ ] 运行了无技能对照，确认失败确实出现
- [ ] 逐字记录了 agent 的自我开脱

**GREEN — 编写最小技能：**
- [ ] 符合概览中的编写不变量（BCP 14 关键词、默认 MANDATORY、单一例外出口、自包含、运行时可移植）
- [ ] `name` 与目录名完全一致
- [ ] `description` 是规范性“在……时使用——你 MUST……”触发条件，包含具体症状，采用第三人称，不概述工作流
- [ ] 指导形式与失败类型匹配（见“按失败类型选择形式”）
- [ ] 针对具体基线失败，没有为未观察到的情况填充内容
- [ ] 内联一个出色示例（不使用多语言）
- [ ] 在技能生效的情况下重跑场景，agent 现已遵守规则

**REFACTOR — 堵住漏洞：**
- [ ] 逐字捕获每个新的自我开脱
- [ ] 为每个自我开脱添加明确否定、自我开脱表行和危险信号条目
- [ ] 将每个作为即将违规症状的新自我开脱加入 `description`
- [ ] 反复测试，直到不再出现新的自我开脱

**质量：**
- [ ] 只在决策并非显然时使用流程图
- [ ] 没有叙事故事、多语言稀释或流程图内代码
- [ ] 辅助文件只用于可复用工具或重型参考材料

## description 字段 — 触发条件

- 编写 `description` 时 → 你 MUST 采用第三人称，使用**“在 `<情形>` 时使用——你 MUST `<核心要求>`”**形式的规范性触发条件。
- 编写 description 时 → 你 MUST NOT 概述技能的工作流。
- 编写触发条件时 → 你 MUST 放入未来 agent 会搜索的词：症状、错误短语，以及表明技能适用的同义词。
