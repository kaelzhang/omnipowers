# 完成前验证

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 铁律

```
没有最新验证证据，就不作完成声明
```

- 验证命令未在本会话运行，或尚未阅读输出 → 你 MUST NOT 声称它要证明的事项已通过、已修复或已完成。

## 闸门

闸门事件 — 准备陈述任何状态、表达满意、声称或暗示成功、完成或正确、提交、开 PR、标记任务完成，或转到下一个任务。

有效证据 — 本会话在当前完全相同的工作树上通过的检查；检查覆盖的任一文件发生改动时，证据失效。

闸门事件 → 你 MUST 按顺序执行：

1. **识别**能证明声明的命令或检查。
2. **运行**到完成，或复用有效证据；不中断运行，不使用记忆中的运行结果。**匹配**检查范围与声明：提交内容的完整连贯性采用足以证明它的最小检查，“测试通过”采用测试集。
3. **阅读**完整输出：退出码和真实的通过 / 失败数量。
4. **比较**输出与声明：
   - 输出确认声明 → 陈述声明，并附上证据。
   - 输出未确认声明 → 陈述真实状态，并附上证据。

- 技能或阶段请求的检查已有有效证据 → 你 MUST NOT 仅因请求而重跑。
- 闸门事件 → 你 MUST NOT 跳过任何步骤。

## 读取命令本身的退出码

- 要用到命令结果 → 命令 MUST NOT 放在管道中运行。
- 要用到命令结果 → 你 MUST 将命令自身的输出重定向到文件，读取命令自身的退出码，再读取文件：

```bash
<command> > <file> 2>&1; echo "exit: $?"
```

## 每种声明所需的证据

| 声明 | 证据 REQUIRED | 不足以证明 |
|---|---|---|
| 测试通过 | 本会话测试命令的输出：0 个失败 | 以前的运行、“应能通过” |
| Linter / 类型检查无误 | 工具输出：0 个错误 | 部分检查、推断 |
| 构建成功 | 构建命令：退出码 0 | “linter 通过了”、“日志看着没问题” |
| bug 已修复 | 重新测试原始症状：通过 | 代码已改、假定已修复 |
| 回归测试有效 | 亲眼看到修复前失败、修复后通过 | 只通过一次 |
| 要求已满足 | 逐行核对要求 | “测试通过了” |
| 委派 / 生成的工作已完成 | 已检查真实 diff 和产物 | 一份“成功”报告 |

## 危险信号 — 停下

发现以下任一情况 → 你 MUST 停下并验证：

- 用“应能”“大概”或“似乎”描述结果
- 用对结果的信心代替最新运行
- 验证前表达满意（“太好了！”、“完美！”、“完成了！”）
- 尚无最新检查就准备提交、推送或开 PR
- 相信成功报告，未亲自检查产物
- 依赖部分检查，或用通过的 linter 证明构建或测试通过
- 通过管道读取检查结果（`| tail`、`| grep`、`| head`）
- “就这一次”，或因疲倦而想尽快结束
- 尚未运行检查，却用任何措辞暗示成功
