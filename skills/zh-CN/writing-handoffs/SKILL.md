# 编写交接文档

> 本文中全大写的规范关键词 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14（RFC 2119、RFC 8174）解释，且仅在全大写时具有规范含义。

## 概览

- 编写交接文档时 → 你 MUST 让交接文档及引用的产物足以支撑完全无法访问本次对话的 agent 继续工作。

## 仅由用户发起

- 用户未明确要求交接或压缩会话 → 本技能 MUST NOT 自行触发。
- 你认为交接有帮助 → 你 MAY 用一句话说明。
- 用户尚未要求交接 → 你 MUST NOT 编写文档。

## 范围 — 按用途确定

- 用户说明了下一次会话的用途 → 交接文档 MUST 围绕此用途确定范围：相关内容写全细节，无关的未完成事项最多留一行指针。
- 用户未说明用途 → 交接文档 MUST 覆盖本次会话中**所有**未完成的工作。

## 要求的章节

编写文档时 → 你 MUST 按以下顺序纳入所有章节，并包含指定内容：

1. **目标** — 工作要实现什么，以及完成的定义。
   - 只阅读目标章节时 → 接手者 MUST 能判断何时停止。
2. **当前状态 — 附证据** — 什么已完成、什么正在进行。
   - 每条“已完成”声明 → 你 MUST 引用实际观察到的验证（测试命令及结果、评审结论、命令输出）。
   - 未经你验证的声明 → 你 MUST 标注为未验证。
3. **产物索引** — 工作涉及或依赖的每份规格、计划、提交、diff 和文件，以**路径、提交哈希或标识符**引用，每项最多用一行说明与工作的关系。
   - 编写交接文档时 → 你 MUST NOT 将产物内容复制进文档。
4. **下一步** — 按顺序列出具体行动。
   - 每一步 → 你 MUST 写得足够具体，让接手者能直接开始，不用重新推导分析。
5. **待解决问题 / 阻塞项** — 每个未决决策、缺失输入和外部阻塞项；没有时明确写“无”。
6. **建议使用的技能** — 接手 agent 要调用的技能及用途。
   - 恢复工作时 → 接手 agent SHOULD 按列明的用途调用建议使用的技能。
   - 编写交接文档时 → “建议使用的技能”章节是 REQUIRED 的。
7. **约束** — 约束这项工作的每条规则：用户在本次会话中提出的偏好、项目规则、已锁定的决策、明确排除的事项。

## 模板

```markdown
# 交接 — <用途>（<日期>）

## 目标
<工作实现什么；完成的定义>

## 当前状态
- 已完成：<事项> — 证据：<观察到的命令/测试/评审及结果>
- 进行中：<事项> — <准确进展>
- 未验证：<事项> — <尚欠验证的原因>

## 产物索引
- <路径 | 提交哈希 | 标识符> — <一行说明它为何重要>

## 下一步
1. <具体、按顺序执行的行动>

## 待解决问题 / 阻塞项
- <事项，或“无”>

## 建议使用的技能
- <技能名称> — <调用用途>

## 约束
- <约束性规则、偏好或已锁定的决策>
```

## 脱敏 — 任何内容写入磁盘前

写入文件前 → 你 MUST 扫描材料中的秘密、凭据、API 密钥、令牌、连接字符串和 PII，并逐一脱敏，不留例外。

## 位置

- 交接位置 — 按 `using-omnipowers` 解析的 `work-state` 位置，回退路径为 `.omnipowers/handoffs/YYYY-MM-DD-<purpose>.md`，其中 `<purpose>` 是简短的 kebab-case 标识。
- 隔离工作区中的交接 — 按 `using-git-worktrees` 的规则返回主干后编写的交接文档。
- 宿主已维护当前 work-state 文档 → 你 MUST 更新这些文档，并将交接文档写成指向它们的指针：当前状态、阻塞项和下一行动只在宿主文档中写一次，在此引用。
- 写完交接文档后 → 你 MUST 向用户报告文件路径。

## 编写规则

- 编写交接文档时 → 你 MUST NOT 引用对话本身（“如上所述”“我们商定的方法”“参见我先前的消息”）；重新陈述实质内容，或指向产物。

## 自我开脱 — 拒绝

| 借口 | 事实 |
|--------|---------|
| “下一个 agent 会自己找出要用的技能” | “建议使用的技能”章节是 REQUIRED 的。 |
